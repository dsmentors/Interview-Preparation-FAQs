RAG fundamentals

Q1What is Retrieval-Augmented Generation (RAG), and what problem does it solve?

RAG is a pattern where the system first retrieves relevant information from an external knowledge source and then passes it to an LLM as context, so the model generates its answer from that information instead of relying only on what it memorized during training.

It solves three problems of a plain LLM:

  • Stale knowledge: the model does not know about events or documents after its training cutoff.
  • Private data: the model has never seen your company documents.
  • Hallucination: with the right facts in the prompt, the model is less likely to invent an answer, and you can show the sources.
Q2What are the main components of a RAG system?

Q3Walk through the end-to-end flow of a RAG system.

RAG has two phases.

Indexing (offline, done once and then updated):

  1. Load and clean the documents.
  2. Split them into chunks and attach metadata (source, page, date).
  3. Convert each chunk into an embedding and store it in a vector database.

Query time (online, for every question):

  1. Embed the user question with the same embedding model.
  2. Retrieve the top-k most similar chunks (optionally rerank them).
  3. Put the chunks and the question into a prompt.
  4. The LLM generates an answer grounded in those chunks, ideally with citations.
Q4RAG vs fine-tuning vs long context: when do you choose which?
RAG Fine-tuning Long context (paste everything)

They are not exclusive: a common setup is a fine-tuned model that follows your output format, combined with RAG for the facts.

Q5What are the limitations of RAG?
  • Retrieval quality is the ceiling: if the right chunk is not retrieved, the LLM cannot answer correctly.
  • Chunking trade-offs: small chunks lose context, large chunks add noise.
  • Weak on global questions: "summarize the whole corpus" or questions that need many documents combined are hard for top-k retrieval.
  • Extra latency and cost: embedding, searching and a longer prompt on every request.
  • Operational work: keeping the index fresh, handling permissions and evaluating quality.
  • Not a guarantee against hallucination: the model can still ignore or misread the context.
Q6What is the difference between naive RAG, advanced RAG and modular RAG?
  • Naive RAG: index, retrieve top-k, generate. Simple, but sensitive to chunking and query wording.
  • Advanced RAG: adds steps around the same flow, such as query rewriting, hybrid search, reranking, metadata filtering and context compression.
  • Modular RAG: treats each step as a swappable module and can route, loop or branch, for example choosing between a vector search, a SQL query or a web search per question.

Ingestion, chunking and embeddings

Q7Why does chunking matter, and how do you choose chunk size and overlap?

Chunks are the unit of retrieval, so their size directly affects quality. Chunks that are too small lose the surrounding context, and chunks that are too large mix several topics, dilute the embedding and waste prompt space.

A common starting point is 200 to 800 tokens with 10 to 20% overlap, then tune it using a small evaluation set. Overlap prevents a sentence or idea from being cut in half at a boundary. The right size depends on the content (FAQs and legal clauses differ) and on the embedding model's input limit.

Q9How do you handle PDFs, tables, scanned pages and images in a RAG pipeline?

Parsing quality often matters more than the model choice.

  • Text PDFs: use a layout-aware parser so headers, footers, columns and page numbers do not pollute the chunks.
  • Scanned documents: run OCR first, and check its output.
  • Tables: keep each table together (for example as Markdown or with a short text summary) instead of splitting it by rows.
  • Images and charts: caption them with a vision model, or use a multimodal embedding model.
  • Always keep metadata: file name, page number and section title, so answers can cite where the information came from.
Q10Why attach metadata to chunks?

Metadata (source, author, date, department, language, access level, document type) lets you:

  • filter results (for example only documents from 2024 or only the HR department),
  • enforce permissions so users only see what they are allowed to see,
  • show citations with file and page,
  • debug which documents a wrong answer came from.
Q11What are embeddings, and how do you choose an embedding model?

An embedding is a vector (a list of numbers) that represents the meaning of a text, so that similar texts end up close together in vector space.

Things to compare when choosing a model:

  • Quality on your domain and language: check a benchmark such as MTEB, then test on your own data.
  • Dimension size: larger vectors can be more accurate but cost more storage and search time.
  • Maximum input length: it limits your chunk size.
  • Cost, latency and hosting: an API or a self-hosted open-source model (for example BGE or E5).
  • Multilingual or multimodal needs.
Q12Cosine similarity vs dot product vs Euclidean distance: which should you use?
  • Cosine similarity measures the angle between vectors and ignores their length. It is the most common choice for text embeddings.
  • Dot product also considers length. For normalized vectors it gives exactly the same ranking as cosine.
  • Euclidean (L2) distance measures straight-line distance. For normalized vectors it also gives the same ranking.

Use the metric the embedding model was trained for, and be consistent between indexing and querying.

Q13Why must the query and the documents use the same embedding model, and what happens if you change the model?

Each model creates its own vector space, so vectors from two different models cannot be compared meaningfully (they may not even have the same dimension).

If you change the embedding model, you must re-embed and re-index every document. Plan for this by storing the original text, keeping the model name and version in your index metadata, and building the new index next to the old one before switching.

Retrieval and vector databases

Q14What is a vector database, and what is approximate nearest neighbor (ANN) search?

A vector database stores embeddings and quickly finds the ones closest to a query vector, usually with metadata filtering as well.

Exact search compares the query with every vector, which gets too slow at millions of vectors. ANN algorithms trade a small loss in recall for a large gain in speed. Common ones:

Index Idea Main knobs
Flat Exact brute-force comparison None, but slow at scale
HNSW A layered graph that is searched by hopping to nearer neighbors M, efConstruction, efSearch
IVF Clusters vectors and searches only the nearest clusters Number of clusters, nprobe
PQ Compresses vectors into short codes to save memory Number of sub-vectors, bits
Q15What is the difference between dense, sparse and hybrid retrieval?
  • Dense retrieval: embedding similarity. It understands meaning and synonyms, but can miss exact terms such as product codes, names or error IDs.
  • Sparse retrieval: keyword-based methods such as BM25. It is excellent for exact terms, but does not understand meaning.
  • Hybrid retrieval: runs both and merges the results, usually giving the best overall recall.

A popular way to merge the two ranked lists is Reciprocal Rank Fusion (RRF):

score(d) = sum over each list of 1 / (k + rank(d))      # k is commonly 60
Q16What is BM25, and when can it beat embeddings?

BM25 is a keyword ranking function. It scores a document higher when it contains the query terms often (with diminishing returns) and when those terms are rare across the collection, and it adjusts for document length.

It can beat embeddings when queries contain exact identifiers: product codes, function names, legal section numbers, rare names or error messages. This is why hybrid search is so common in production.

Q17What is reranking, and why add it?

The first retrieval step is fast but approximate. A reranker takes the top candidates (for example 20 to 100) and reorders them with a more accurate model, and you keep only the best few for the prompt.

Bi-encoder (embedding retrieval) Cross-encoder (reranker)
How it scores Encodes query and document separately, then compares vectors Reads query and document together
Speed Fast, vectors can be pre-computed Slow, runs per query-document pair
Accuracy Good Higher
Used for First-stage retrieval over the whole corpus Second-stage reordering of a short list
Q18How do you choose top-k and a similarity threshold?
  • Top-k: too small and you miss the answer, too large and you add noise and cost. Start with 3 to 5 chunks for the prompt (retrieving 20 to 50 first if you rerank), then tune on an evaluation set.
  • Similarity threshold: drop results below a minimum score so the model is not fed irrelevant text. It also lets the system answer "I don't know" when nothing relevant is found.

Scores are not comparable across different embedding models, so tune the threshold per model.

Q19What is Maximal Marginal Relevance (MMR)?

MMR is a re-selection method that balances relevance to the query with diversity among the chosen chunks. It avoids returning five near-identical chunks that all say the same thing.

MMR = argmax [ λ * sim(query, doc) - (1 - λ) * max sim(doc, already_selected) ]

A higher λ favors relevance, a lower λ favors diversity.

Q20What is metadata filtering, and what is the difference between pre-filtering and post-filtering?

Metadata filtering restricts the search to chunks that match conditions such as date, department or user permissions.

  • Pre-filtering: apply the filter first, then search only the matching vectors. It returns the full top-k, but support and performance depend on the vector database and index type.
  • Post-filtering: search first, then remove results that do not match. It is simple, but you may end up with fewer than k results, or none.

Q22How do you keep a RAG index up to date?
  • Incremental updates: re-embed only new or changed documents, detected by a content hash or modified date.
  • Deletions: remove the old chunks when a document is deleted or replaced, otherwise outdated answers keep appearing.
  • Stable IDs: give every chunk an ID derived from its document and position so it can be updated cleanly.
  • Versioning: store the embedding model and chunking settings, and rebuild the index when they change.
  • Scheduling: run the sync on a schedule or trigger it from document change events.

Advanced RAG techniques

Q23What is query rewriting, query expansion and HyDE?

User questions are often short or vague, so the system improves the query before searching:

  • Query rewriting: an LLM rewrites the question into a clearer, standalone search query.
  • Query expansion: adds synonyms or related terms.
  • HyDE (Hypothetical Document Embeddings): the LLM first writes a hypothetical answer, and that text is embedded and used for the search. A made-up answer is often closer to real documents in vector space than the short question is.
Q24How do you handle multi-hop or complex questions?

Questions like "Which team owns the service that caused last week's outage?" need information from several places.

  • Query decomposition: break the question into sub-questions, retrieve for each, then combine the results.
  • Multi-query retrieval: generate several phrasings of the question, retrieve for all of them and merge.
  • Iterative or agentic retrieval: retrieve, read, decide what is still missing, and retrieve again.
  • GraphRAG: use a knowledge graph when relationships between entities matter.
Q25What is parent-document (small-to-big) retrieval?

Small chunks are best for matching a query precisely, while large chunks give the LLM enough context. Small-to-big does both: it searches over small chunks, but then returns the larger parent section (or the neighboring chunks) to the LLM.

Q26What is contextual compression?

Retrieved chunks often contain a lot of irrelevant text. Contextual compression shortens them before they reach the LLM, either by extracting only the sentences relevant to the question, or by dropping chunks that fail a relevance check. It saves tokens and reduces noise, at the cost of one extra step.

Q27What is GraphRAG, and when is it useful?

GraphRAG builds a knowledge graph (entities and their relationships) from the documents, often with summaries of related groups of entities, and retrieves from that graph instead of, or together with, plain text chunks.

It is useful for questions about relationships and the big picture ("what are the main themes across these reports?"), which top-k chunk retrieval handles poorly. The cost is a heavier and more expensive indexing process.

Q28What are agentic RAG, Self-RAG and Corrective RAG (CRAG)?
  • Agentic RAG: an LLM agent decides whether to retrieve, which tool or source to use, and whether to search again.
  • Self-RAG: the model learns to decide when to retrieve and to critique its own retrieved context and output.
  • Corrective RAG (CRAG): a lightweight evaluator scores the retrieved documents. If they look wrong or weak, the system falls back to another source such as a web search or rewrites the query.

The common idea: add a feedback step so bad retrieval is caught before the answer is generated.

Q29How do you handle follow-up questions in a conversational RAG chatbot?

A follow-up such as "and what about the second one?" cannot be searched as it is. The usual fix is question condensation: use the chat history and the new message to ask an LLM to rewrite a standalone question, then retrieve with that. Also decide how much history to keep, so the prompt does not grow without limit.

Q30What is multimodal RAG?

Multimodal RAG retrieves and uses more than text: images, charts, tables, audio or video. Two common approaches:

  • Convert to text: caption images and summarize tables, then use normal text retrieval.
  • Multimodal embeddings: embed images and text in the same vector space and pass the retrieved images to a vision-capable LLM.

Generation and prompting

Q31How do you prompt the LLM to use the retrieved context and avoid hallucinating?

Give clear rules in the prompt:

Answer the question using ONLY the context below.
If the answer is not in the context, reply "I don't know".
Quote the source name for every fact you use.

Context:
{retrieved_chunks}

Question: {question}

Other helpful steps: keep the temperature low, ask for citations, and add a check that verifies the answer is supported by the context.

Q32How do you make a RAG system cite its sources?

Store the source, page and section as metadata on every chunk, and give each retrieved chunk an ID in the prompt (for example [1], [2]). Ask the model to reference those IDs for every claim, then map them back to document links in the UI. Verify citations automatically if possible, because models can cite the wrong chunk.

Q33What is the “lost in the middle” problem, and how do you reduce it?

LLMs tend to use information at the beginning and the end of a long context better than information in the middle. If the key chunk is buried in the middle of many chunks, it may be ignored.

To reduce it: send fewer, better chunks (rerank and compress), put the most relevant chunks first or last, and avoid padding the prompt with low-value text.

Q34What do you do if the retrieved context is larger than the model’s context window?
  • Retrieve fewer chunks, or rerank and keep only the best.
  • Compress or summarize the chunks.
  • Map-reduce: summarize or answer per chunk group, then combine the partial results.
  • Iterative refinement: go through chunks one by one and update the answer.
  • Use a model with a larger context window if the cost is acceptable.

Evaluation and production

Q35How do you evaluate a RAG system?

Evaluate retrieval and generation separately, using a test set of real questions with known answers and source documents.

Stage Metric What it tells you
Retrieval Recall@k / hit rate Was the right chunk among the top k?
Retrieval MRR, nDCG Was the right chunk ranked high?
Retrieval Context precision How much of the retrieved text was actually relevant?
Generation Faithfulness (groundedness) Is the answer supported by the retrieved context?
Generation Answer relevance Does the answer address the question?
End to end Correctness, latency, cost, user feedback Does it work for real users?

Frameworks such as RAGAS automate several of these using an LLM as a judge. Always spot-check with human review.

Q36Your RAG chatbot gives wrong answers. How do you debug it?

Find out which stage failed, in this order:

  1. Was the right information in the index? If not, it is an ingestion problem: parsing, missing documents, bad chunking.
  2. Was the right chunk retrieved? Print the top-k for the failing question. If not, try hybrid search, better chunk size, query rewriting, a different embedding model or a reranker.
  3. Was the right chunk in the final prompt? Check truncation, ordering and the lost-in-the-middle effect.
  4. Did the LLM use it correctly? If the context was right but the answer wrong, improve the prompt, lower the temperature, or use a stronger model.

Log the question, retrieved chunks, prompt and answer for every request so you can do this analysis.

Q37How do you reduce the latency and cost of a RAG application?
  • Cache embeddings, retrieval results and frequent answers.
  • Tune ANN search parameters and keep the index in memory.
  • Retrieve fewer chunks, and rerank only a short candidate list.
  • Compress context so the prompt is shorter.
  • Route easy questions to a smaller, cheaper model.
  • Stream the answer so users see output sooner.
  • Run independent steps (for example several searches) in parallel.
Q38What security risks does RAG introduce, and how do you handle them?
  • Access control leaks: a user must only retrieve documents they are allowed to read. Enforce permissions with metadata filters at retrieval time, not in the prompt.
  • Prompt injection through documents: a retrieved document can contain instructions such as "ignore previous instructions". Treat retrieved text as untrusted data, keep it clearly separated from instructions, and limit what the model can do with tools.
  • Sensitive data: mask or exclude personal and confidential data before indexing.
  • Multi-tenancy: keep each customer's data isolated, for example in separate indexes or namespaces.
Q39How should a RAG system respond when no relevant documents are found?

It should say so, instead of guessing. Use a similarity threshold or a relevance check to detect weak retrieval, and instruct the model to reply "I don't know" or ask a clarifying question. Optionally fall back to another source (for example web search) and show that the answer came from there.

Q40How would you design a question-answering assistant over a company’s internal documents?
  1. Clarify requirements: who the users are, document types and volume, expected accuracy, latency, privacy and access rules.
  2. Ingestion: connectors for each source, layout-aware parsing, chunking with metadata (source, date, owner, permissions).
  3. Index: an embedding model plus a vector database with metadata filtering, and BM25 for hybrid search.
  4. Retrieval: query rewriting, hybrid search, permission filtering, then reranking.
  5. Generation: a grounded prompt, low temperature, citations, and an "I don't know" path.
  6. Evaluation: a test set of real questions, retrieval and faithfulness metrics, and user feedback buttons.
  7. Operations: incremental re-indexing, logging, monitoring of latency and cost, and guardrails against prompt injection.
Q41Can you show a minimal RAG example in Python?

This example uses the sentence-transformers library for embeddings and NumPy for the similarity search. In a real system you would use a vector database and call an LLM at the end.

from sentence_transformers import SentenceTransformer
import numpy as np

docs = [
    "Employees get 24 days of paid leave per year.",
    "Remote work requires manager approval.",
    "Expense claims must be filed within 30 days.",
]

model = SentenceTransformer("all-MiniLM-L6-v2")
doc_vecs = model.encode(docs, normalize_embeddings=True)

def retrieve(query, k=2):
    q = model.encode([query], normalize_embeddings=True)[0]
    scores = doc_vecs @ q                 # cosine similarity (vectors are normalized)
    top = np.argsort(-scores)[:k]
    return [(docs[i], float(scores[i])) for i in top]

question = "How many vacation days do I get?"
context = "\n".join(text for text, _ in retrieve(question))

prompt = f"""Answer using ONLY the context below.
If the answer is not in the context, say "I don't know".

Context:
{context}

Question: {question}"""
