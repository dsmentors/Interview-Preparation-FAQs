Data warehousing fundamentals

Q1What is a data warehouse, and why do organizations need one?

A data warehouse is a central repository that collects, cleans and stores data from many source systems (applications, databases, files) in a form designed for reporting and analysis, rather than for day-to-day transactions.

Organizations need it to get a single, consistent view of the business, to keep history for trend analysis, to run heavy analytical queries without slowing down operational systems, and to give BI tools one trusted place to read from.

Q2What are the characteristics of a data warehouse (Inmon’s definition)?
  • Subject-oriented: organized around business subjects such as sales, customers and products, not around applications.
  • Integrated: data from different sources is cleaned and made consistent (naming, formats, units, codes).
  • Time-variant: it keeps historical data, so you can analyze change over time.
  • Non-volatile: data is loaded and read, but not updated or deleted in the normal way, so history is preserved.

Q5What are the layers of a typical data warehouse architecture?
  1. Source systems: ERP, CRM, applications, files, APIs.
  2. Staging area: a temporary landing zone where raw extracted data is stored before it is transformed.
  3. Data warehouse (core) layer: the cleaned, integrated and modeled data.
  4. Data marts: subject-specific subsets built for particular teams.
  5. Presentation / BI layer: dashboards, reports and ad hoc analysis tools (Power BI, Tableau).

Metadata, data quality, security and orchestration run across all layers.

Many real projects use a mix of both.

Q7What is a data mart?

A data mart is a smaller, focused part of a data warehouse built for a specific team or subject (sales, finance, HR). It is easier to understand, faster to query and can have its own access rules. A dependent data mart is loaded from the central warehouse, while an independent one is built straight from source systems, which risks inconsistent numbers.

Q8What is an Operational Data Store (ODS)?

An ODS is an intermediate store with current, lightly integrated operational data, refreshed frequently (minutes or hours). It supports operational reporting and is often used as a source or staging layer for the warehouse. Unlike the warehouse, it holds little history and its data may be updated.

Dimensional modeling

Q9What is a star schema?

A star schema has a central fact table (the measurable business events) surrounded by dimension tables (the descriptive context: who, what, where, when). The fact table holds foreign keys to the dimensions plus numeric measures, and the diagram looks like a star.

SELECT d.year, p.category, SUM(f.sales_amount) AS total_sales
FROM fact_sales f
JOIN dim_date d    ON f.date_key = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
GROUP BY d.year, p.category
ORDER BY d.year, total_sales DESC;

It is simple, easy to understand and fast for aggregations.

Q10What is a snowflake schema, and how does it differ from a star schema?

In a snowflake schema the dimension tables are normalized into several related tables (for example product → subcategory → category).

Star schema Snowflake schema
Dimensions Denormalized (one table per dimension) Normalized (split into sub-tables)
Joins Fewer, simpler queries More joins, more complex
Query speed Usually faster Usually slower
Storage Some redundancy Less redundancy
Maintenance Easier to understand Easier to update shared attributes

Star schemas are generally preferred for BI because of simplicity and performance.

Q12What is the grain of a fact table, and why is it important?

The grain is what one row in the fact table represents, for example “one line item on an order” or “one account per day”. It is the first and most important design decision, because it decides which dimensions apply and how the data can be analyzed. Always declare the grain before choosing dimensions and measures, and never mix different grains in one fact table.

Q14What are additive, semi-additive and non-additive measures?
  • Additive: can be summed across all dimensions, for example sales amount or quantity.
  • Semi-additive: can be summed across some dimensions but not time, for example an account balance (you can add balances across accounts, but not across days).
  • Non-additive: cannot be summed at all, for example ratios, percentages and unit prices. Store the numerator and denominator instead, and calculate the ratio after aggregating.
Q15What is a surrogate key, and why use it instead of the natural key?

A surrogate key is a system-generated, meaningless integer that uniquely identifies a dimension row. It is preferred because it:

  • allows history tracking (several rows for the same customer, as in SCD Type 2),
  • is independent of source system keys, which can change, be reused or conflict between systems,
  • is small and fast to join,
  • and lets you handle unknown or missing members with special keys.

The natural (business) key is still stored as an attribute.

Q16What are Slowly Changing Dimensions (SCD), and what are the main types?

SCDs describe how a warehouse handles dimension attributes that change over time (a customer moves city, a product changes category).

Type How it works History kept?
Type 0 Never changes; keep the original value Original only
Type 1 Overwrite the old value No
Type 2 Add a new row with effective dates and a current flag Full history
Type 3 Add a column for the previous value Limited (one previous value)
Type 6 A hybrid of types 1, 2 and 3 Full history plus current value

Type 2 is the most common when history matters.

Q17How do you implement SCD Type 2 in SQL?

Add effective_from, effective_to and is_current columns to the dimension. Then close the old row and insert a new current row for changed or new customers:

-- 1) close the current row of customers whose city changed
UPDATE dim_customer
SET effective_to = CURRENT_DATE, is_current = 0
WHERE is_current = 1
  AND customer_id IN (SELECT s.customer_id
                      FROM stg_customer s
                      JOIN dim_customer d ON d.customer_id = s.customer_id AND d.is_current = 1
                      WHERE d.city <> s.city);

-- 2) insert a new current row for new and changed customers
INSERT INTO dim_customer (customer_id, name, city, effective_from, effective_to, is_current)
SELECT s.customer_id, s.name, s.city, CURRENT_DATE, NULL, 1
FROM stg_customer s
LEFT JOIN dim_customer d ON d.customer_id = s.customer_id AND d.is_current = 1
WHERE d.customer_id IS NULL OR d.city <> s.city;

The surrogate key is generated automatically for each new row.

Q18What are conformed dimensions?

A conformed dimension is a dimension (such as Date, Customer or Product) that has the same structure, keys and meaning in every fact table and data mart that uses it. Conformed dimensions are what allow you to combine and compare data from different business processes (for example sales and returns by the same customer and product) and are the backbone of Kimball’s bus architecture.

Q19What are junk, degenerate and role-playing dimensions?
  • Junk dimension: combines several low-cardinality flags and indicators (for example payment type, gift-wrap yes/no) into one small dimension, instead of cluttering the fact table.
  • Degenerate dimension: a dimension key stored directly in the fact table with no dimension table, such as an invoice or order number.
  • Role-playing dimension: one physical dimension used several times in a fact table for different roles, such as the Date dimension used as order date, ship date and delivery date.
Q20Why does a data warehouse usually need a date dimension?

A date dimension has one row per day with many ready-made attributes: day of week, week, month, quarter, year, fiscal period, holiday and weekend flags. It lets analysts group, filter and compare by time without calculating these values in every query, and it supports business calendars that normal date functions do not know.

ETL and ELT

Q21What is ETL, and what are its steps?

ETL stands for Extract, Transform, Load:

  1. Extract: read data from the source systems (databases, files, APIs).
  2. Transform: clean and reshape it: fix errors, remove duplicates, standardize formats, apply business rules, join and aggregate.
  3. Load: write the result into the target data warehouse tables.

Transformation traditionally happens in a separate ETL server or tool, before loading.

Q22What is the difference between ETL and ELT?
ETL ELT
Order Extract → Transform → Load Extract → Load → Transform
Where transformation runs In the ETL tool or a separate engine Inside the target warehouse or lakehouse
Raw data Often not kept Kept in the warehouse, so it can be reprocessed
Fits best with On-premises warehouses, strict cleansing before loading Cloud warehouses with scalable compute (Snowflake, BigQuery)
Flexibility Lower, a change needs re-running the pipeline Higher, transformations are SQL on data already loaded
Q23What is a staging area, and why use it?

A staging area is an intermediate area where extracted data is landed first, usually as an unchanged copy of the source. It reduces the load on source systems (data is extracted once), lets you validate and reprocess without going back to the source, and separates extraction from transformation. Staging tables are usually truncated and reloaded for every run.

Q24What is the difference between full load and incremental load?
  • Full load: the whole dataset is extracted and the target is reloaded every time. Simple, but slow and costly for large tables.
  • Incremental (delta) load: only new or changed records since the last run are extracted and applied. It is faster and cheaper, but needs a way to detect changes and more careful logic.

Initial loads are usually full, and later runs are incremental.

Q25What is Change Data Capture (CDC), and what are the ways to do it?

CDC identifies and captures changes (inserts, updates, deletes) in the source so that only they are loaded. Common methods:

  • Log-based: reads the database transaction log. It has little impact on the source and captures deletes (tools such as Debezium).
  • Timestamp or version column: select rows where last_modified is later than the last run. Simple, but it misses hard deletes.
  • Triggers: database triggers record changes in a separate table. They add load to the source.
  • Snapshot comparison: compare today’s extract with the previous one. Heavy for big tables.
Q26What kinds of transformations are performed in ETL?
  • Cleansing: fix or remove invalid, missing and inconsistent values.
  • Deduplication.
  • Standardization: consistent formats, units, codes and date formats.
  • Type conversion and parsing.
  • Joins and lookups to enrich data (for example mapping a product code to a category).
  • Aggregation and derived columns (for example profit = revenue − cost).
  • Applying business rules and surrogate key assignment.
  • Splitting or merging fields and rows.
Q27How do you load data into the warehouse using MERGE (upsert)?

An upsert updates rows that already exist and inserts the ones that do not, in one statement:

MERGE INTO dim_customer AS t
USING stg_customer AS s
  ON t.customer_id = s.customer_id
WHEN MATCHED AND (t.email <> s.email OR t.city <> s.city) THEN
  UPDATE SET t.email = s.email, t.city = s.city
WHEN NOT MATCHED THEN
  INSERT (customer_id, name, email, city)
  VALUES (s.customer_id, s.name, s.email, s.city);

This is an SCD Type 1 style load (it overwrites). The MERGE syntax is supported by SQL Server, Oracle, Snowflake and BigQuery, with small differences between them.

Q28What is the difference between batch and real-time (streaming) data integration?
  • Batch: data is processed in scheduled groups (hourly, nightly). It is simpler, cheaper and fine when reports can be slightly out of date.
  • Real-time / streaming: data is processed continuously, as events arrive, using tools such as Kafka, Spark Structured Streaming or Flink. It is needed for fraud detection, live dashboards and alerts, but is more complex and costly to build and run.

A common choice is micro-batching (every few minutes) as a middle ground.

Q29How do you design ETL jobs to be restartable and idempotent?

An idempotent job gives the same result if it is run more than once, so a rerun after a failure does not create duplicates.

  • Use MERGE/upsert or delete-then-insert for the target slice instead of blind inserts.
  • Load by batch or partition (for example one day), so a failed batch can be re-run on its own.
  • Keep audit and control tables with run IDs, start and end times, row counts and status, and checkpoints of the last successful load.
  • Make each step atomic (a transaction, or a staging table swapped in at the end).

Modern data platforms and cloud warehouses

Q31What are the features of a modern cloud data warehouse (Snowflake, BigQuery, Redshift, Synapse)?
  • Separation of storage and compute (in most), so each scales independently.
  • Elastic, pay-for-use scaling.
  • Columnar storage and massively parallel processing (MPP) for fast analytics.
  • Support for semi-structured data (JSON, Parquet).
  • Little infrastructure management (some are fully serverless, such as BigQuery).
  • Built-in security, sharing and governance features.
Q32What is columnar storage, and why is it good for analytics?

A columnar database stores each column’s values together instead of storing complete rows. Analytical queries usually read a few columns from many rows, so the database reads only the columns it needs, and similar values stored together compress very well. This makes aggregations much faster than in a row-based store, which is better for transactional work.

Q33What is the medallion architecture (bronze, silver, gold)?

A layered design for a lakehouse that improves data quality step by step:

  • Bronze: raw data as ingested from the sources, kept unchanged.
  • Silver: cleaned, validated, deduplicated and conformed data.
  • Gold: business-level, aggregated and modeled data (for example star schemas) ready for BI and machine learning.
Q34What is a lakehouse, and what are Delta Lake and Apache Iceberg?

A lakehouse adds warehouse features (ACID transactions, schema enforcement, time travel, SQL) on top of low-cost data lake storage, so BI and data science can use the same data. Delta Lake, Apache Iceberg and Apache Hudi are open table formats that provide these features on files in object storage.

Q35What does dbt do?

dbt (data build tool) handles the transformation (T) in ELT. Analysts write transformations as SQL SELECT statements, and dbt builds them as tables or views inside the warehouse, in the right dependency order. It adds version control, automated tests, documentation and lineage to analytics code.

Q36What is a data pipeline orchestrator, and what is a DAG?

An orchestrator (Apache Airflow, Prefect, Dagster) schedules, runs and monitors the steps of a pipeline, handles dependencies and retries, and raises alerts. Pipelines are defined as a DAG (Directed Acyclic Graph): tasks are nodes, arrows show which task must finish before another starts, and there are no cycles.

Performance, quality and governance

Q37How do you improve query performance in a data warehouse?
  • Design: use a star schema, an appropriate grain and sensible data types.
  • Partitioning large tables (for example by date) so queries scan only the needed partitions (partition pruning).
  • Clustering or sort keys and distribution keys (in MPP systems) so related data sits together.
  • Pre-aggregated tables or materialized views for common summaries.
  • Indexes where the platform uses them (mainly on traditional databases).
  • Select only needed columns and filter early, and avoid unnecessary joins.
  • Columnar formats and compression.
Q38What are the dimensions of data quality?
Dimension Question it answers
Accuracy Does the data reflect reality?
Completeness Is all the required data present?
Consistency Is it the same across systems and tables?
Timeliness Is it available and up to date when needed?
Uniqueness Are there duplicate records?
Validity Does it follow the required format, type and rules?
Q39How do you check data quality and validate ETL results?
  • Row-count reconciliation between source, staging and target.
  • Control totals (sum of amounts) and checksums compared with the source.
  • Null, duplicate and range checks on key columns.
  • Referential integrity (every fact key has a matching dimension row).
  • Business-rule tests and comparison with trusted reports.
  • Automated tests and monitoring in the pipeline (for example with dbt tests or Great Expectations), with alerts and a place to store rejected records.
Q40What is metadata, and why does it matter?

Metadata is data about data.

  • Technical metadata: table and column names, data types, sources, load times, lineage.
  • Business metadata: definitions, owners, rules and KPI formulas.
  • Operational metadata: run history, row counts, durations and errors.

It helps people find and trust data, and supports impact analysis and audits. A data catalog (for example Alation, Collibra or built-in cloud catalogs) manages it.

Q41What is data lineage?

Data lineage shows where data came from, how it was transformed and where it is used, from source systems to reports. It helps to trace errors back to the source, assess the impact of a change (“what breaks if I change this column?”), and meet audit and compliance needs.

Q42What is Master Data Management (MDM)?

MDM creates and maintains one trusted, consistent version of key business entities (customer, product, supplier) across all systems. It matches and merges duplicate records (for example the same customer in CRM and billing) and creates a “golden record” that the warehouse and applications can use.

Q43How do you secure a data warehouse?
  • Role-based access control with least privilege.
  • Row-level and column-level security for sensitive data.
  • Data masking and encryption at rest and in transit.
  • Audit logs of access and changes.
  • Separate environments (development, test, production).
  • Compliance with privacy regulations (for example GDPR), including retention and deletion rules.

Scenarios and design questions

Q44Design question: how would you design a data warehouse for an e-commerce company?
  1. Business questions: sales by product, category, region and channel; customer retention; marketing performance.
  2. Choose the process and the grain: for sales, “one row per order line”.
  3. Dimensions: Date, Product, Customer, Store or Channel, Promotion, Geography.
  4. Fact table: fact_sales with date, product, customer and channel keys, an order number (degenerate dimension), quantity, sales amount and discount.
  5. Other facts: returns, inventory snapshots and web events, sharing conformed dimensions.
  6. History: SCD Type 2 for customer and product attributes that change.
  7. Pipeline: extract from the order system, CRM and web analytics with CDC into staging, transform and load with ELT, orchestrated with Airflow.
  8. Quality and governance: reconciliation checks, lineage, access control.
  9. Serving: a BI layer (Power BI or Tableau) on the star schema, with aggregates for heavy dashboards.
Q45An ETL job failed halfway through the night. What do you do?
  1. Check the job logs and the audit table to find the failed step, the error and how many rows were processed.
  2. Fix the cause (data issue, connection, a changed source schema, resources).
  3. Make sure the target is not left half-loaded: roll back, or clean up the partial batch.
  4. Re-run from the failed step or batch, which is safe if the job is idempotent.
  5. Reconcile row counts and totals, and tell downstream users if reports were delayed.
  6. Add the missing check or alert, and document the incident to prevent a repeat.
Q46How do you handle late-arriving data and late-arriving dimensions?
  • Late-arriving facts (a sale recorded days later): load them with the correct business date, and make sure aggregates and snapshots can be reprocessed for the affected period.
  • Late-arriving dimensions (a fact arrives before its customer record): insert an “inferred” placeholder dimension row with the business key, load the fact against it, and update the row with the real attributes when the dimension data arrives (and create a new SCD2 version if needed).
Q47How do you handle deleted records in the source system?

Deletes are easy to miss in incremental loads. Options: use log-based CDC, which captures deletes, ask the source to use soft deletes (an is_deleted flag), compare the keys in the source with the keys in the warehouse to find the missing ones, or run a periodic full reconciliation. In the warehouse, mark records as deleted or inactive instead of removing them, to preserve history.

Q48How do you test an ETL pipeline?
  • Unit tests of individual transformation rules with sample data.
  • Source-to-target reconciliation (counts, sums, samples).
  • Data quality tests (nulls, duplicates, referential integrity, valid values).
  • Incremental load tests: inserts, updates and deletes are all applied correctly.
  • Re-run (idempotency) tests: running twice does not create duplicates.
  • Performance and volume tests with realistic data sizes.
  • Regression tests after each change, ideally in a CI pipeline.
Q49How would you migrate data from a legacy system to a new data warehouse?
  1. Profile and understand the source data, rules and quality issues.
  2. Map source fields to the target model and agree on transformations with the business.
  3. Build and test the extraction, cleansing and loading in a test environment.
  4. Do an initial full load, then incremental loads to keep up with changes.
  5. Reconcile with the legacy reports, with the business validating the numbers.
  6. Run both systems in parallel for a period, then cut over with a rollback plan.
  7. Document the lineage and retire the legacy system.
