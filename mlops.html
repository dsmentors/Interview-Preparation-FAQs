MLOps fundamentals

Q1What is MLOps, and why is it needed?

MLOps (Machine Learning Operations) is the set of practices, tools and culture for taking machine learning models from experiments to reliable production systems and keeping them working. It combines machine learning, software engineering (DevOps) and data engineering.

It is needed because a model that works in a notebook is only a small part of a real ML system. In production you must also handle data pipelines, reproducibility, deployment, monitoring, retraining, security and collaboration between data scientists, engineers and operations teams.

Q2What is the difference between DevOps and MLOps?
DevOps MLOps
What is versioned and tested Code Code, data and models
Why things break Code changes Code changes, data changes and model decay
Testing Unit and integration tests The same, plus data validation and model evaluation
Pipeline CI/CD CI/CD plus continuous training (CT)
Monitoring Latency, errors, uptime The same, plus data drift, prediction quality and fairness
Reproducibility Same code gives same build Needs the same code, data, parameters and environment
Q3What are the stages of the machine learning lifecycle?
  1. Problem definition: the business goal and the success metric.
  2. Data collection and preparation: ingestion, cleaning, labeling, validation.
  3. Feature engineering.
  4. Model training and experimentation: tracking runs, tuning.
  5. Evaluation and validation: offline metrics, fairness and robustness checks.
  6. Deployment: packaging and releasing the model as a service or batch job.
  7. Monitoring: system health, data quality, model performance.
  8. Retraining and improvement, which feeds back into the earlier stages.
Q4Why do many ML projects fail to reach production?
  • Unclear business goal or success metric.
  • Poor data quality or availability in production compared with the experiment.
  • Notebook code that is not reproducible, tested or deployable.
  • Training-serving skew: features computed differently offline and online.
  • No monitoring, so model decay goes unnoticed.
  • Lack of ownership between data science, engineering and operations.
  • Cost, latency or compliance requirements discovered too late.
Q5What are CI, CD and CT in MLOps?
  • Continuous Integration (CI): automatically test and validate every change to the code, and also the data and model (for example schema checks and minimum accuracy).
  • Continuous Delivery/Deployment (CD): automatically package and release the pipeline or the model service to the target environment.
  • Continuous Training (CT): automatically retrain the model on new data, on a schedule or when monitoring shows a problem, then validate and register the new version.
Q6What are the MLOps maturity levels?

A commonly used model (popularized by Google) describes three levels:

Level Description
Level 0: manual Data scientists train in notebooks and hand over a model manually. Releases are rare, and there is no monitoring or automation.
Level 1: pipeline automation Training is an automated pipeline with data validation, so the model can be retrained continuously (CT).
Level 2: CI/CD pipeline automation The pipeline code itself is tested, built and deployed automatically, so teams can experiment and release quickly and safely.

Data and experiment management

Q7Why do you need data versioning, and which tools are used?

A model is the result of code + data + parameters. If the data changes and you cannot recover the old version, you cannot reproduce or debug a model. Data versioning stores snapshots (or hashes) of datasets, linked to the code version that used them.

Common tools: DVC (works with Git and remote storage), lakeFS (Git-like branches for data lakes), and table formats with time travel such as Delta Lake or Apache Iceberg.

Q8What is experiment tracking, and how do you do it with MLflow?

Experiment tracking records, for every training run, the parameters, metrics, code version, data version and artifacts (such as the model file), so runs can be compared and reproduced. Popular tools are MLflow, Weights & Biases and Neptune.

import mlflow
import mlflow.sklearn
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import accuracy_score

mlflow.set_experiment("churn-model")

with mlflow.start_run():
    model = RandomForestClassifier(n_estimators=200, max_depth=8, random_state=42)
    model.fit(X_train, y_train)

    mlflow.log_params({"n_estimators": 200, "max_depth": 8})
    mlflow.log_metric("accuracy", accuracy_score(y_test, model.predict(X_test)))
    mlflow.sklearn.log_model(model, "model")
Q9How do you make an ML experiment reproducible?
  • Version everything: code (Git), data (DVC or similar), configuration and parameters.
  • Fix random seeds where possible.
  • Pin the environment: exact package versions, a lock file or a Docker image.
  • Track runs automatically with an experiment tracker.
  • Keep training pipelines as code instead of manual notebook steps.
  • Record the hardware when results are sensitive to it (for example GPU non-determinism).
Q10What is a model registry?

A model registry is a central place that stores versioned models together with their metadata (metrics, training data version, owner) and their lifecycle stage, for example staging, production and archived. It gives a controlled path to production: a model is registered, validated, approved and then promoted, and you can roll back to an earlier version. MLflow Model Registry and the registries in SageMaker, Vertex AI and Azure ML are examples.

Q11What is a feature store, and what problem does it solve?

A feature store is a system for defining, storing and serving features consistently for both training and prediction.

  • The offline store holds historical feature values for training (point-in-time correct, to avoid leakage).
  • The online store serves the latest values with low latency for real-time prediction.

It solves training-serving skew, avoids duplicate feature work across teams and makes features reusable. Examples: Feast, Tecton, and the feature stores built into cloud ML platforms.

Q12What is data validation in an ML pipeline?

Data validation automatically checks incoming data before training or prediction: expected schema and types, missing values, value ranges, allowed categories, duplicates, and distribution changes compared with the training data. A failed check should stop the pipeline or raise an alert, so bad data does not silently produce a bad model. Tools include Great Expectations, TensorFlow Data Validation and Pandera.

Q13What is training-serving skew, and how do you prevent it?

Training-serving skew is a difference between how features are computed or what data looks like during training versus in production, so the model performs worse live than in testing. Causes include different code paths for features, different data sources and different preprocessing.

Prevent it by using the same feature code or a feature store for both, packaging preprocessing together with the model, logging the features used at prediction time, and comparing training and serving distributions.

Pipelines, testing and CI/CD

Q14What is an ML pipeline, and which tools orchestrate it?

An ML pipeline is an automated, repeatable sequence of steps such as data ingestion → validation → feature engineering → training → evaluation → registration → deployment. Each step has defined inputs and outputs, so it can be rerun, scheduled and monitored.

Orchestration tools include Apache Airflow, Kubeflow Pipelines, Prefect, Dagster, and managed services such as SageMaker Pipelines and Vertex AI Pipelines.

Q15How do you test machine learning systems?
Test type What it checks
Unit tests Preprocessing and feature functions
Data tests Schema, ranges and quality of the data
Model tests Minimum metrics, performance on important slices of data, comparison with the current production model
Behavioral tests Invariance and sanity checks (for example changing an irrelevant word should not change a prediction)
Integration tests The full pipeline and the serving API end to end
Load tests Latency and throughput under expected traffic
Q16What does a CI pipeline for an ML project look like?

On every pull request the pipeline should lint and unit test the code, validate the data, and run a short training and evaluation to check that the model meets a minimum quality bar.

name: ml-ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest tests/
      - run: python scripts/validate_data.py
      - run: python scripts/evaluate_model.py --min-accuracy 0.85
Q17When and how should a model be retrained?

Common retraining triggers:

  • Schedule: daily, weekly or monthly, depending on how quickly data changes.
  • Performance drop detected by monitoring.
  • Data drift above a threshold.
  • New labeled data becomes available.
  • Business or product changes.

An automated retraining run should validate the data, train, evaluate against the current production model, and only promote the new model if it is better and passes all checks.

Q18How do you package a model for deployment?
  • Serialization formats: joblib or pickle (Python only), ONNX (portable across frameworks and runtimes), SavedModel or TorchScript, or the MLflow model format.
  • Include preprocessing with the model (for example a scikit-learn Pipeline) so serving matches training.
  • Containerize the model and its dependencies with Docker.
  • Security note: never load a pickle file from an untrusted source, because it can run arbitrary code.
Q19How would you containerize an ML model service with Docker?
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Good practices: pin dependency versions, use a small base image, copy the requirements file first so Docker can cache the install layer, run as a non-root user, and keep model files versioned (for example loaded from a registry or object storage at startup).

Deployment and serving

Q20What are the different ways to deploy a model?
Mode How it works Typical use Latency
Batch Runs on a schedule and writes predictions to a table or file Recommendations, churn scores, reports Minutes to hours
Online (real-time) A REST or gRPC service answers each request Fraud checks, search ranking Milliseconds
Streaming Scores events as they flow through a stream Anomaly detection, live personalization Seconds or less
Edge / on-device The model runs on the user’s device Mobile apps, IoT, privacy-sensitive cases Very low, works offline
Q21What options exist for serving models?
  • A custom API (for example FastAPI or Flask) around the model: simple and flexible.
  • Model servers: BentoML, TorchServe, TensorFlow Serving, NVIDIA Triton, KServe or Seldon, which add batching, versioning and optimized inference.
  • Managed endpoints: SageMaker, Vertex AI and Azure ML, which handle scaling and monitoring for you.
  • Serverless functions for light, spiky workloads.

Choose based on latency needs, traffic, model size, team skills and cost.

Q22What are the common release strategies for new models?
Strategy How it works Benefit
Shadow deployment The new model receives real traffic and predicts, but its output is not used Safe comparison on real data
Canary release A small share of traffic goes to the new model, increased gradually Limits the impact of problems
A/B test Traffic is split between models and a business metric is compared Proves real business impact
Blue-green Two identical environments, switch traffic from old to new Instant rollback

Always keep the previous version ready so you can roll back quickly.

Q23How do you scale inference and reduce latency?
  • Autoscaling replicas based on traffic, for example in Kubernetes.
  • Dynamic batching of requests, especially on GPUs.
  • Caching frequent predictions or features.
  • Model optimization: quantization, pruning, distillation or a faster runtime such as ONNX Runtime.
  • Use the right hardware (CPU for small models, GPU for large ones).
  • Precompute predictions in a batch when real-time scoring is not required.
Q24What role do Docker and Kubernetes play in MLOps?
  • Docker packages the model, code and dependencies into an image that runs the same everywhere.
  • Kubernetes runs and manages many containers: scaling, rolling updates, self-healing, resource limits and GPU scheduling.

Together they give reproducible, scalable deployments. Many ML platforms, such as Kubeflow and KServe, are built on Kubernetes.

Q25What are the main cloud ML platforms?
  • AWS SageMaker
  • Google Vertex AI
  • Azure Machine Learning
  • Databricks (with MLflow)

They offer managed training, pipelines, registries, deployment endpoints and monitoring. The trade-off is convenience and speed versus cost and vendor lock-in, so teams sometimes combine them with open-source tools.

Q26How do you version and roll back models in production?

Give every model a unique version in the registry, linked to its code, data and metrics. Deploy by version and keep the previous production version available. To roll back, redeploy or point the traffic back to the earlier version, with an automatic trigger for clear failures (error rate or latency above a threshold). Keep prediction logs tagged with the model version so you can analyze each one.

Q27What are the main considerations when deploying an LLM application (LLMOps)?

LLMOps extends MLOps with concerns specific to large language models:

  • Prompt and configuration versioning, as well as model versions.
  • Evaluation with test sets and LLM-as-judge, since outputs are open-ended.
  • Monitoring quality, hallucinations, safety, latency and token cost.
  • Guardrails and protection against prompt injection.
  • RAG data pipelines and vector index updates.
  • Serving costs and latency: caching, streaming and model routing.

Monitoring and maintenance

Q28What should you monitor in a production ML system?
Layer Examples
System Latency, throughput, error rate, CPU/GPU and memory use, cost
Data Missing values, schema changes, out-of-range values, drift in inputs
Model Accuracy or other quality metrics (when labels arrive), prediction distribution, drift in outputs
Business Conversion, revenue, user feedback, fairness across groups
Q29What is the difference between data drift, concept drift and prediction drift?
Type What changes Example
Data (covariate) drift The distribution of the input features Customers become younger on average
Concept drift The relationship between inputs and the target Fraudsters change their behavior, so the same inputs now mean something different
Prediction (label) drift The distribution of the model’s outputs (or of the true labels) The share of “high risk” predictions suddenly doubles

Data drift does not always hurt accuracy, but concept drift usually does.

Q30How do you detect data drift?

Compare the current data with a reference (usually the training data) for each feature:

  • Kolmogorov-Smirnov (KS) test for numeric features.
  • Chi-square test for categorical features.
  • Population Stability Index (PSI): a common rule of thumb is below 0.1 stable, 0.1 to 0.25 moderate change, above 0.25 major change.
  • Statistical distances such as Jensen-Shannon or Wasserstein.
from scipy.stats import ks_2samp

stat, p_value = ks_2samp(train_df["age"], live_df["age"])
if p_value < 0.01:
    print("Possible drift in 'age'")

Tools such as Evidently automate these reports and dashboards.

Q31How do you monitor model quality when true labels arrive late or never?

In many systems, labels come weeks later (for example fraud chargebacks) or never. Use proxy signals in the meantime:

  • input data drift and prediction distribution changes,
  • model confidence scores,
  • business metrics and user behavior (clicks, overrides, complaints),
  • agreement with a reference or shadow model,
  • sampling a small set of predictions for manual review or labeling.

Compute the real metrics and compare when labels become available.

Q32How do alerting and automated responses work in ML monitoring?

Define thresholds for each metric (for example PSI above 0.25, accuracy below a minimum, latency above a limit), send alerts to the responsible team, and decide the action: investigate, roll back to the previous model, or trigger a retraining pipeline. Avoid too many alerts by tuning thresholds, otherwise the team will start ignoring them.

Q33Why do models degrade over time, and how do you handle it?

Models degrade because the real world changes: user behavior, seasonality, new products, data pipeline changes and upstream bugs. Handle it with monitoring, regular retraining on fresh data, a feedback loop that collects new labels, and a process that compares each new model with the current one before promoting it.

Q34What is a feedback loop in ML systems, and what risks does it have?

A feedback loop collects what happened after a prediction (clicks, outcomes, corrections) and uses it as new training data. The risk is that the model influences the data it learns from: a recommender only sees clicks on what it showed, so it can reinforce its own bias, or a fraud model only gets labels for transactions it flagged. Reduce this with exploration (randomly showing alternatives), unbiased samples for evaluation and regular review of data sources.

Governance, scale and design

Q35What is model governance, and what should be documented?

Governance makes sure models are accountable, auditable and compliant. Document:

  • the purpose, owner and intended use of the model,
  • data sources and lineage,
  • training approach, metrics and limitations (a model card),
  • fairness and bias checks,
  • approvals and version history,
  • monitoring results and incidents.

It is especially important in regulated areas such as finance and healthcare.

Q36What security and privacy points matter in MLOps?
  • Access control for data, models and pipelines (least privilege).
  • Secrets management: never put credentials in code or notebooks.
  • Privacy: minimize and anonymize personal data, and follow regulations.
  • Supply chain: scan dependencies and base images, and do not load untrusted pickle files.
  • Model protection: guard against model theft, adversarial inputs and leakage of training data.
  • Audit logging of who changed or deployed what.
Q37What is technical debt in ML systems?

ML systems have the usual software debt plus ML-specific debt: tangled pipelines (changing one thing changes everything), undeclared dependencies on other models or data, unstable data sources, glue code around libraries, feedback loops, and configuration that is not versioned. The remedies are modular pipelines, clear interfaces and data contracts, tests, monitoring and regular clean-up.

Q38How do you control the cost of ML systems?
  • Use spot or preemptible instances for training that can restart.
  • Right-size hardware and shut down idle resources.
  • Cache results and use batch prediction where real-time is not needed.
  • Optimize models (quantization, smaller models) for serving.
  • Avoid retraining more often than needed.
  • Track cost per prediction and per project.
Q39How do you choose MLOps tools?

Consider the team’s skills, the existing cloud and tech stack, scale and latency needs, open-source vs managed trade-offs, integration with the other tools, security and compliance requirements, and the total cost. Start with a small, simple toolchain (for example Git, DVC, MLflow, Docker and a CI system) and add components only when a clear problem justifies them.

Q40Design question: how would you build an end-to-end MLOps pipeline for a fraud detection model?
  1. Requirements: decision latency (for example under 100 ms), acceptable false positives, regulation and explainability needs.
  2. Data and features: transaction streams plus history, with a feature store so training and real-time scoring use the same features. Validate the data.
  3. Training pipeline: orchestrated and scheduled (for example weekly), handling the class imbalance, with every run tracked in MLflow.
  4. Evaluation: precision-recall and cost-based metrics, checks on important slices of data, and comparison with the current production model.
  5. Registry and CI/CD: register the model, run tests, and deploy through a container to an online service.
  6. Release: shadow mode first, then a canary release, with an easy rollback.
  7. Monitoring: latency and errors, data and prediction drift, and quality metrics when delayed labels (chargebacks) arrive.
  8. Retraining and feedback: triggers from drift or new labels, plus human review of uncertain cases.
  9. Governance: audit logs, model documentation, access control and privacy protection.
