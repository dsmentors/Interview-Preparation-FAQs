Git fundamentals

Q1What is Git, and how is it different from GitHub?

Git is a distributed version control system that records the history of changes to your files, so you can go back to earlier versions, work on features in parallel and collaborate without overwriting each other’s work. "Distributed" means every developer has a full copy of the repository and its history, so most operations work offline.

GitHub, GitLab and Bitbucket are hosting services built around Git. They add remote storage, pull requests, code review, issue tracking and CI/CD.

Q2What are the three areas of Git (working directory, staging area and repository)?
Area What it is Moved with
Working directory The files you are editing on disk Your editor
Staging area (index) A preview of what will go into the next commit git add
Repository (.git) The permanent history of commits git commit

The staging area lets you choose exactly which changes go into each commit.

Q3What are the basic Git commands in a daily workflow?
git clone <url>              # copy a remote repository
git status                   # see changed and staged files
git add file.py              # stage a file (git add . stages everything)
git commit -m "Add feature"  # save the staged changes as a commit
git pull                     # get the latest changes from the remote
git push                     # upload your commits to the remote
git log --oneline            # view the commit history
git diff                     # see unstaged changes
Q4What is the difference between git fetch and git pull?
  • git fetch downloads new commits and branches from the remote but does not change your working files or current branch. It is safe, and lets you review the changes first.
  • git pull is git fetch followed by a merge (or a rebase with git pull --rebase) into your current branch.
Q5What is the difference between clone, fork and branch?
  • Clone: copies a repository to your computer.
  • Fork: copies someone else’s repository to your own account on the hosting service, so you can change it freely and propose changes back through a pull request.
  • Branch: a separate line of development inside the same repository.
Q6What is HEAD, and what is a detached HEAD?

HEAD is a pointer to the commit you are currently on, normally through the current branch.

A detached HEAD happens when you check out a specific commit or tag instead of a branch. New commits then do not belong to any branch and can be lost. To keep that work, create a branch from there:

git switch -c my-new-branch
Q7What is .gitignore, and how do you stop tracking a file that is already committed?

.gitignore lists file patterns Git should not track, such as __pycache__/, .env, *.log, virtual environments and large data files.

It does not affect files that are already tracked. To stop tracking one:

git rm --cached secrets.env     # remove from Git but keep the file on disk
echo "secrets.env" >> .gitignore
git commit -m "Stop tracking secrets.env"

Branching and merging

Q8What is a branch, and why use branches?

A branch is a lightweight, movable pointer to a commit, which gives you an isolated line of work. Teams use one branch per feature or fix, so unfinished work does not affect the main code, and it can be reviewed before it is merged.

git switch -c feature/login     # create and switch to a new branch
git switch main                 # switch back
git branch -d feature/login     # delete a merged branch

(git checkout -b feature/login does the same in older Git versions.)

Q9What is the difference between git merge and git rebase?
Merge Rebase
What it does Combines two branches, usually creating a merge commit Replays your commits on top of another branch
History Preserves the real history, which can look branched Creates a linear history
Commit IDs Unchanged Rewritten (new commits)
Safe on shared branches Yes No, avoid rebasing commits that others already have

A common practice is to rebase your own local feature branch onto the latest main to keep it up to date, then merge it through a pull request.

Q10What is a fast-forward merge?

A fast-forward happens when the branch you merge into has not moved since your branch was created. Git simply moves the branch pointer forward, with no merge commit. If both branches have new commits (they have diverged), Git creates a three-way merge with a merge commit instead. You can force a merge commit with git merge --no-ff.

Q11What is a merge conflict, and how do you resolve it?

A conflict occurs when Git cannot automatically combine changes, usually because both branches changed the same lines. Git marks the file:

<<<<<<< HEAD
your version
=======
their version
>>>>>>> feature/login

To resolve it:

  1. Open the conflicted files (git status lists them) and edit them to the correct final content, removing the markers.
  2. Stage the files: git add <file>.
  3. Finish with git commit (for a merge) or git rebase --continue (for a rebase).

You can cancel with git merge --abort.

Q12What is git cherry-pick?

It applies one specific commit from another branch onto your current branch, creating a new commit with the same changes.

git cherry-pick <commit-hash>

It is useful for copying a bug fix to a release branch without merging the whole branch.

Q13What is git stash, and when do you use it?

git stash temporarily saves your uncommitted changes and returns the working directory to a clean state, so you can switch branches without committing half-finished work.

git stash              # save the changes
git switch other-branch
git stash pop          # bring the changes back (and remove them from the stash)
git stash list         # see saved stashes
Q14What are the common branching strategies?
Strategy How it works Best for
GitHub Flow main is always deployable; short-lived feature branches merged by pull request Teams that deploy often
Git Flow Long-lived main and develop branches, plus feature, release and hotfix branches Scheduled releases and several versions in production
Trunk-based development Everyone commits small changes to main (the trunk) often, using feature flags Mature CI/CD teams that need fast integration

Undoing changes and fixing mistakes

Q15What is the difference between git reset, git revert and git restore?
Command What it does Safe on shared history?
git revert <commit> Creates a new commit that undoes an earlier commit Yes
git reset Moves the branch pointer back, removing commits from the history No, rewrites history
git restore <file> Discards changes in a file or unstages it Local only

git reset has three modes:

  • --soft: moves HEAD only; the changes stay staged.
  • --mixed (default): resets the staging area; the changes stay in the working directory.
  • --hard: also discards the changes in the working directory (destructive).
Q16How do you undo the last commit or change its message?
git commit --amend -m "Better message"   # change the message (or add staged changes) of the last commit
git reset --soft HEAD~1                  # undo the commit, keep the changes staged
git reset --hard HEAD~1                  # undo the commit and DISCARD the changes
git revert HEAD                          # safe way if the commit was already pushed

Avoid amending or resetting commits that you have already pushed and others may have pulled.

Q17How do you recover a deleted branch or lost commits?

Use git reflog, which records where HEAD has been (for a limited time, 90 days by default for reachable entries). Find the commit hash and recreate the branch:

git reflog
git switch -c recovered-branch <commit-hash>
Q18What do you do if you accidentally commit a password or API key?
  1. Revoke and rotate the secret immediately. Assume it is compromised, even if you remove it, because it may already be in clones, forks or logs.
  2. Remove it from the history using a tool such as git filter-repo or BFG Repo-Cleaner, then force-push (coordinate with the team).
  3. Add the file to .gitignore and use environment variables or a secrets manager from now on.
  4. Consider adding a pre-commit secret scanner.
Q19What is interactive rebase, and what is it used for?

git rebase -i HEAD~3 lets you edit the last three commits before sharing them: squash several commits into one, reword messages, reorder or drop commits. It is used to keep history clean (for example squashing “fix typo” commits) and, like all rebasing, should only be done on commits that have not been shared.

Q20What is git bisect?

It finds the commit that introduced a bug using binary search. You mark one commit as good and one as bad, and Git checks out the middle commit for you to test. After a few steps it points to the first bad commit.

git bisect start
git bisect bad            # the current commit is broken
git bisect good v1.0      # this older version worked
# test, then run `git bisect good` or `git bisect bad` until Git finds the culprit
git bisect reset

Collaboration and good practice

Q21What is a pull request, and what does a good code review process look like?

A pull request (PR, or merge request in GitLab) proposes merging a branch into another and is the place for review, discussion and automated checks.

Good practice: keep PRs small and focused, write a clear description, make CI run tests and linting before review, require at least one approval, respond to comments constructively, and merge only when checks pass.

Q22What is the difference between a lightweight tag and an annotated tag?

Tags mark specific commits, usually releases such as v1.0.0.

  • Lightweight tag: just a name pointing to a commit.
  • Annotated tag: a full Git object with the tagger, date and message, and it can be signed. It is recommended for releases.
git tag -a v1.0.0 -m "First release"
git push origin v1.0.0
Q23How do you work with remotes, and why use --force-with-lease?
git remote -v                       # list remotes
git remote add origin <url>         # add a remote
git push -u origin feature/login    # push and set the upstream branch

After rewriting your own branch (for example with a rebase), you must force-push. Prefer git push --force-with-lease, which refuses to overwrite the remote branch if someone else has pushed new commits you do not have, unlike a plain --force.

Q24What makes a good commit and a good commit message?
  • One logical change per commit, so it is easy to review, revert and bisect.
  • A short summary line (about 50 characters) in the imperative mood: “Add login validation”.
  • A body that explains why the change was made, when it is not obvious.
  • Do not commit generated files, secrets, large datasets or model files. Use .gitignore, Git LFS for large binary files, or a tool such as DVC for data and models.

Docker fundamentals

Q25What is Docker, and what is a container?

Docker is a platform for building, shipping and running applications in containers. A container is a lightweight, isolated process that packages the application together with its libraries and dependencies, so it runs the same way on a laptop, a server or the cloud. It solves the “works on my machine” problem.

Q26What is the difference between a container and a virtual machine?
Container Virtual machine
Operating system Shares the host OS kernel Runs a full guest OS on a hypervisor
Size Megabytes Gigabytes
Startup Seconds or less Minutes
Isolation Process-level (good) Stronger, hardware-level
Resource use Light, many per host Heavier
Q27What is the difference between a Docker image and a container?
  • An image is a read-only template made of layers: the application code, runtime, libraries and settings.
  • A container is a running instance of an image, with a thin writable layer on top.

An image is like a class, and a container is like an object created from it. You can start many containers from one image. Images are stored in a registry such as Docker Hub.

Q28How does Docker work internally (client, daemon, registry)?
  • The Docker client (the docker command) sends commands to the Docker daemon (dockerd) through an API.
  • The daemon builds images and creates, runs and manages containers, networks and volumes.
  • A registry stores and distributes images (docker pull and docker push).

Containers use Linux features: namespaces for isolation and cgroups for resource limits.

Q29What are the most common Docker commands?
docker build -t myapp:1.0 .                  # build an image from a Dockerfile
docker run -d -p 8000:8000 --name api myapp:1.0   # run a container in the background
docker ps                                    # list running containers (-a shows all)
docker logs -f api                           # follow the logs
docker exec -it api sh                       # open a shell inside a running container
docker stop api                              # stop gracefully
docker rm api                                # remove a stopped container
docker images                                # list images
docker rmi myapp:1.0                         # remove an image
docker pull python:3.11-slim                 # download an image
docker push myuser/myapp:1.0                 # upload an image to a registry

Useful docker run options: -d (background), -p host:container (publish a port), -v (mount a volume), -e (environment variable), --rm (delete when it exits).

Q30Why is Docker useful in data science and machine learning projects?
  • Reproducible environments: the same Python version and library versions everywhere.
  • Easy sharing and deployment of models and APIs.
  • Isolation between projects with conflicting dependencies.
  • Portability between a laptop, cloud servers and Kubernetes.
  • Consistency between training, testing and production environments, which supports MLOps pipelines.

Dockerfile and images

Q31What is a Dockerfile, and what are its main instructions?

A Dockerfile is a text file with step-by-step instructions to build an image.

Instruction Purpose
FROM The base image to start from
WORKDIR Sets the working directory
COPY / ADD Copies files into the image
RUN Runs a command while building (for example pip install)
ENV Sets an environment variable
EXPOSE Documents the port the app listens on
USER Sets the user to run as
CMD / ENTRYPOINT Defines what runs when the container starts
Q32What is the difference between CMD and ENTRYPOINT?
  • ENTRYPOINT sets the main executable that always runs.
  • CMD provides the default command or default arguments, which are easy to override at docker run.
ENTRYPOINT ["python", "app.py"]
CMD ["--port", "8000"]

docker run myimage runs python app.py --port 8000, and docker run myimage --port 9000 replaces only the CMD part. With only CMD, anything you add after the image name replaces the whole command.

Q33What is the difference between COPY and ADD?

Both copy files into the image. ADD also extracts local tar archives and can download from URLs, which makes its behavior less obvious. Best practice is to use COPY unless you specifically need those extra features.

Q34What are image layers, and how does build caching work?

Each instruction creates a layer. Docker caches layers and reuses them when the instruction and everything before it has not changed. When a layer changes, all the following layers are rebuilt.

So order instructions from least to most frequently changing: install dependencies first, copy your source code last.

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # cached unless requirements change
COPY . .                                              # changes often, so it comes last
Q35What is a multi-stage build, and why use it?

A multi-stage build uses several FROM stages in one Dockerfile. You build or compile in an early stage with all the tools, then copy only the results into a small final image. The final image is smaller and has fewer security risks.

FROM python:3.11 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
CMD ["python", "app.py"]
Q36How do you reduce the size of a Docker image?
  • Use a slim or minimal base image (python:3.11-slim; Alpine can cause compatibility issues with some Python packages).
  • Use multi-stage builds.
  • Add a .dockerignore file to leave out .git, data, virtual environments and notebooks.
  • Use pip install --no-cache-dir, and clean package caches in the same RUN step.
  • Combine related commands, and install only what you need.
Q37Why should you avoid the latest tag?

latest is just a default tag name, not a guarantee of the newest or a stable version, and it can change under you. Using it makes builds non-reproducible and can break deployments unexpectedly. Pin specific versions (for example python:3.11.9-slim, or myapp:1.4.2) in Dockerfiles and deployments.

Volumes, networking and Docker Compose

Q38What is the difference between volumes, bind mounts and tmpfs?

Container storage is temporary: data in the writable layer is lost when the container is removed. To keep it:

Type What it is Typical use
Volume Storage managed by Docker Databases and persistent data in production
Bind mount A host folder mounted into the container Development: edit code on the host and see it in the container
tmpfs Stored in the host’s memory only Temporary or sensitive data 
docker run -v mydata:/var/lib/postgresql/data postgres:16
Q39How does networking work in Docker?
  • bridge (default): containers on the same host get private IPs and can talk to each other. On a user-defined bridge, containers can reach each other by name.
  • host: the container shares the host’s network (no isolation, no port mapping needed).
  • none: no network.
  • overlay: connects containers across several hosts (Swarm, Kubernetes-style setups).

To reach a container from outside, publish a port with -p 8000:8000.

Q40What is the difference between EXPOSE and publishing a port with -p?

EXPOSE in a Dockerfile only documents which port the application uses. It does not make the port reachable from outside. -p host_port:container_port (or ports: in Compose) actually publishes the port on the host.

Q41What is Docker Compose, and when do you use it?

Docker Compose defines and runs multi-container applications with one YAML file, for example an API plus a database.

services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/app
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass
      - POSTGRES_DB=app
    volumes:
      - db_data:/var/lib/postgresql/data

volumes:
  db_data:

docker compose up -d      # start everything
docker compose down       # stop and remove the containers

Services reach each other by service name (here db). The passwords above are for demonstration only; use secrets in real projects.

Q42How do you handle environment variables and secrets in Docker?

Pass settings at run time with -e, --env-file or environment: in Compose, instead of writing them in the image. Never put secrets in the Dockerfile, in ENV, or in files copied into the image, because they stay in the image layers. Use the secret features of your platform (Docker secrets, Kubernetes secrets or a secrets manager).

Q43What are Docker restart policies?

They control what happens when a container exits: no (default, never restart), on-failure (restart only on errors), always (restart whenever it stops) and unless-stopped (like always, but not after you stopped it manually).

docker run -d --restart unless-stopped myapp:1.0

Docker in practice

Q44How would you containerize a FastAPI or ML model service?
FROM python:3.11-slim
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .
RUN useradd -m appuser
USER appuser

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

docker build -t ml-api:1.0 .
docker run -d -p 8000:8000 ml-api:1.0

For large model files, mount them as a volume or download them from a registry or storage at startup, instead of baking them into every image.

Q45A container exits immediately after starting. How do you debug it?
  1. docker ps -a shows the container and its exit code.
  2. docker logs <container> shows the error output.
  3. Check the CMD or ENTRYPOINT: a container stops when its main process ends, for example when the app crashes or runs in the background.
  4. Start a shell in the image to investigate: docker run -it --entrypoint sh myimage.
  5. Use docker inspect to check the configuration, environment variables and mounts.
Q46What are the Docker security best practices?
  • Run as a non-root user (USER).
  • Use minimal, trusted base images and pin versions.
  • Scan images for vulnerabilities (for example Trivy or Docker Scout).
  • Keep secrets out of images.
  • Limit resources and capabilities, and use a read-only filesystem where possible.
  • Keep Docker and the base images updated.
Q47How do Git and Docker fit together in a CI/CD pipeline?
  1. A developer pushes code to a Git branch and opens a pull request.
  2. The CI system runs tests and checks on the change.
  3. After the merge, CI builds a Docker image from the Dockerfile and tags it with the version or commit hash.
  4. The image is pushed to a registry.
  5. The deployment step (a server, Docker Compose or Kubernetes) pulls that exact image and runs it, so what was tested is what runs in production.
Q48What is the difference between Docker Swarm and Kubernetes?

Both are container orchestrators that run containers across many machines.

  • Docker Swarm is built into Docker, simple to set up, with fewer features.
  • Kubernetes is the industry standard: more complex, but with powerful scaling, rolling updates, self-healing, a large ecosystem and wide cloud support.

Most production systems today use Kubernetes or a managed service built on it.

CI/CD fundamentals

Q49What is CI/CD, and why is it used?

CI/CD stands for Continuous Integration and Continuous Delivery (or Deployment). It is the practice of automatically building, testing and releasing code every time a change is made, instead of doing those steps by hand.

  • CI: developers merge small changes into a shared branch often, and each merge triggers an automated build and test run.
  • CD: code that passes the checks is automatically prepared for release, or released, to an environment.

It is used to catch bugs early, avoid painful last-minute integration problems and make releases fast and repeatable.

Q50What is the difference between Continuous Integration, Continuous Delivery and Continuous Deployment?
Practice What happens automatically Production release
Continuous Integration Build and test on every merge or pull request Not covered
Continuous Delivery CI plus packaging and deployment to staging, so every passing change is ready to release A person approves it (manual step)
Continuous Deployment Everything above, plus deployment to production Fully automatic, no manual approval

The abbreviation CD is used for both delivery and deployment, so it is worth asking which one a team means.

Q51What are the typical stages of a CI/CD pipeline?
  1. Source: a push, pull request or tag triggers the pipeline and the code is checked out.
  2. Build: install dependencies and compile or package the code.
  3. Static checks: linting, formatting and type checks.
  4. Test: unit tests first, then integration tests.
  5. Security scan: dependency and image vulnerability scans, and secret detection.
  6. Package: create the artifact, such as a Docker image, and push it to a registry.
  7. Deploy to staging and run smoke or end-to-end tests.
  8. Deploy to production (with approval in Continuous Delivery), then monitor.

Cheap, fast checks run first so that the pipeline fails early and saves time.

Q52What is a quality gate in a pipeline?

A quality gate is a condition that must pass before a change can move to the next stage or be merged. If the gate fails, the pipeline stops.

  • All tests pass.
  • Code coverage stays above an agreed threshold.
  • Linting and type checks are clean.
  • No critical vulnerabilities are found.
  • Required code reviews are approved.

On GitHub or GitLab you enforce this with branch protection rules that require the pipeline checks to pass before a pull request can be merged.

Q53What is a build artifact, and why should you build once and deploy the same artifact everywhere?

An artifact is the output of a build that gets deployed, for example a Docker image, a Python wheel, a JAR file or a trained model file. Artifacts are stored in a registry or artifact repository such as Docker Hub, GitHub Container Registry, Amazon ECR, Nexus or Artifactory.

The same artifact is promoted from staging to production, so what was tested is exactly what ships. Rebuilding for each environment can produce subtle differences, such as a different dependency version. Tag artifacts with a version or the commit hash, and avoid relying on the latest tag, so you always know what is running and can roll back to a specific version.

Q54What is pipeline as code, and what can trigger a pipeline?

Pipeline as code means the pipeline is defined in a file stored in the repository, for example .github/workflows/*.yml (GitHub Actions), .gitlab-ci.yml (GitLab CI) or a Jenkinsfile. The pipeline is then versioned, reviewed in pull requests and reproducible, instead of being configured by clicking in a web interface.

Common triggers:

  • A push to a branch or a pull request.
  • A tag or a release, often used to publish.
  • A schedule (cron), for example a nightly build or dependency scan.
  • A manual run, for example workflow_dispatch in GitHub Actions.
  • Another pipeline or an external webhook.

CI tools and pipeline configuration

Q55What are the main concepts in GitHub Actions?
Concept Meaning
Workflow An automated process defined in a YAML file in .github/workflows/
Event What starts the workflow, such as push, pull_request or schedule
Job A group of steps that run on the same runner. Jobs run in parallel unless you set needs
Step One task in a job: a shell command (run) or a reusable action (uses)
Runner The machine that executes a job, either GitHub-hosted or self-hosted
Action A reusable unit of work, such as actions/checkout
Q56Write a basic GitHub Actions workflow that runs tests for a Python project.
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest

On every push to main and on every pull request, it checks out the code, installs Python 3.11, installs the dependencies (with the pip cache enabled) and runs pytest. If any step fails, the job fails and the pull request shows a failed check.

Q57How do GitHub Actions, GitLab CI and Jenkins compare?
Aspect GitHub Actions GitLab CI/CD Jenkins
Config file YAML in .github/workflows/ .gitlab-ci.yml Jenkinsfile (Groovy)
Hosting Built into GitHub, hosted runners available Built into GitLab, hosted or self-managed runners Self-hosted server you maintain
Strength Easy start, large marketplace of actions Everything in one platform Very flexible, huge plugin ecosystem
Trade-off Tied to GitHub Tied to GitLab You manage upgrades, plugins and security

The concepts (stages, jobs, runners, artifacts, secrets) are the same across tools, so learning one makes the others easy.

Q58What is a Jenkinsfile? Show a simple declarative pipeline.

A Jenkinsfile is the pipeline definition stored in the repository for Jenkins. The declarative syntax is the structured, beginner-friendly form: a pipeline contains stages, and each stage contains steps.

pipeline {
    agent any
    stages {
        stage('Install') {
            steps { sh 'pip install -r requirements.txt' }
        }
        stage('Test') {
            steps { sh 'pytest' }
        }
        stage('Build image') {
            steps { sh 'docker build -t ml-api:${BUILD_NUMBER} .' }
        }
    }
    post {
        failure { echo 'Pipeline failed' }
    }
}

agent says where the pipeline runs, stages are the phases shown in the Jenkins interface, and the post block runs actions after the pipeline finishes, for example on failure.

Q59How do you handle secrets in a CI/CD pipeline?

Store secrets in the CI platform’s secret store (for example GitHub Actions secrets or GitLab CI variables marked as masked) and read them at run time. They are masked in logs.

steps:
  - name: Deploy
    run: ./deploy.sh
    env:
      API_TOKEN: ${{ secrets.API_TOKEN }}
  • Never commit secrets to Git, and never print them in logs.
  • Give each secret the least privilege it needs and rotate it regularly.
  • Prefer short-lived credentials, for example OIDC federation to a cloud provider, over long-lived keys.
  • Be careful with pull requests from forks: GitHub does not pass repository secrets to them by default, which prevents malicious code from stealing them.
  • Add a secret scanner (for example gitleaks) to catch accidental commits.
Q60How do caching and matrix builds make a pipeline better?

Caching stores files that are expensive to recreate, such as downloaded dependencies or Docker layers, so later runs reuse them. In the workflow above, cache: pip does this for Python packages.

A matrix build runs the same job several times with different values, for example Python versions or operating systems, in parallel. It proves the code works in every supported combination.

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.10", "3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest

This creates three parallel jobs, one for each Python version.

Deployment strategies and releases

Q61What environments are used in a delivery pipeline, and how does code move between them?
  • Development: where developers run and test their changes, locally or in a shared environment.
  • Staging (or QA): a copy of production used for integration and acceptance tests.
  • Production: what real users use.

The same artifact is promoted from one environment to the next after the checks pass, and only configuration (environment variables, database URLs, secrets) changes between them. Staging should look as much like production as practical, otherwise it cannot catch environment-specific bugs.

Q62What is the difference between rolling, blue-green and canary deployments?
Strategy How it works Rollback Trade-off
Rolling Replace instances gradually, a few at a time Roll the update back the same way Old and new versions run together for a while
Blue-green Run two identical environments, then switch all traffic from blue (old) to green (new) Switch traffic back instantly Needs double the resources
Canary Send a small share of traffic (for example 5%) to the new version, then increase it if metrics look healthy Send traffic back to the old version Needs good monitoring and traffic control

Canary limits the number of users affected by a bad release, and blue-green gives the fastest rollback.

Q63How do you roll back a bad deployment?

Because artifacts are versioned, the safest rollback is to redeploy the previous known-good version.

  • Kubernetes: kubectl rollout undo deployment/<name> returns to the previous revision.
  • Blue-green: switch traffic back to the old environment.
  • Feature flag: turn the new feature off without redeploying.
  • Git: use git revert to create a new commit that undoes the change, then let the pipeline deploy it. Avoid rewriting shared history with git reset --force.

Database changes make rollback harder, so write migrations that are backward compatible (for example add a column first and remove the old one in a later release).

Q64What are feature flags, and how do they relate to CI/CD?

A feature flag (or toggle) is a switch in the code or in a configuration service that turns a feature on or off at run time, without a new deployment.

They separate deploying code from releasing a feature. Unfinished work can be merged to the main branch often and deployed safely while hidden, which supports trunk-based development. Flags also allow gradual rollouts to a percentage of users and act as an instant kill switch when something breaks.

The downside is extra code paths, so remove flags once a feature is fully released.

Q65What is Infrastructure as Code, and why is it used in CI/CD?

Infrastructure as Code (IaC) means defining servers, networks, databases and other infrastructure in files that are stored in Git, instead of creating them by hand in a console. Common tools are Terraform and AWS CloudFormation for provisioning, and Ansible for configuring machines.

  • Environments are reproducible, so staging and production can be created from the same definition.
  • Changes go through pull requests and review and have a history.
  • The pipeline can create, update or destroy infrastructure automatically.
  • It removes manual “snowflake” servers that nobody can rebuild.
Q66What is GitOps?

GitOps is a way of operating infrastructure and deployments where Git is the single source of truth for the desired state of the system. To change production, you open a pull request that changes the configuration files, and you do not run commands against the cluster directly.

An agent running in the cluster, such as Argo CD or Flux, continuously compares the cluster with the repository and pulls and applies any difference. This gives you an audit trail through Git history, easy rollbacks by reverting a commit, and automatic correction if someone changes the cluster by hand.

CI/CD for Docker, ML and real-world scenarios

Q67How do you build and push a Docker image from a CI pipeline?

The pipeline logs in to the registry using secrets, builds the image from the Dockerfile and pushes it with a tag that identifies the commit, so every image can be traced back to its code.

name: Build and push image

on:
  push:
    branches: [main]

jobs:
  docker:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: myuser/ml-api:${{ github.sha }}

Tagging with the commit hash (github.sha) instead of only latest gives exact versions to deploy and roll back to. The registry token is stored as a secret and is never written in the file.

Q68How is CI/CD for machine learning different from CI/CD for normal software?

An ML system changes because of code, data and models, not just code, so the pipeline needs extra steps. This practice is called MLOps.

  • Data validation: check schema, missing values and distribution before training.
  • Continuous training (CT): retrain automatically on a schedule or when new data or drift appears.
  • Model evaluation as a gate: a new model is promoted only if it beats the current one on agreed metrics.
  • Versioning: track data (for example with DVC), experiments and models (for example in an MLflow model registry), together with the code commit.
  • Monitoring after deployment: watch prediction quality, data drift and latency, since a model can degrade without any code change.
Q69What is the difference between trunk-based development and Gitflow, and which suits CI/CD better?
Aspect Trunk-based development Gitflow
Branches One main branch plus short-lived branches (hours to a day or two) Long-lived develop, plus feature, release and hotfix branches
Merge frequency Very often, at least daily When a feature or release is finished
Unfinished work Hidden behind feature flags Kept on its own branch
Fits Continuous delivery and deployment Scheduled, versioned releases

Trunk-based development fits CI/CD better, because the idea of integrating continuously breaks down when branches live for weeks and merge conflicts pile up.

Q70Your pipeline fails randomly, and re-running it makes it pass. What do you do?

This is a flaky failure. Re-running until green hides the problem and teaches the team to ignore failures, so I would find the cause.

  • Compare the logs of failed and passed runs to see which test or step fails.
  • Look for the usual causes: tests that depend on each other or on run order, shared state, timing and sleeps, random data without a fixed seed, and calls to real external services or networks.
  • Fix the cause: isolate state, set seeds, mock external calls and wait for conditions instead of fixed delays.
  • If a fix will take time, quarantine the test so it does not block everyone, and track it until fixed.
  • Record the flaky-test rate so the issue stays visible.
Q71Your pipeline takes 40 minutes. How do you speed it up?

I would first measure which stages take the most time, then work on those.

  • Cache dependencies and Docker layers, and order the Dockerfile so rarely changing layers come first.
  • Run independent jobs in parallel, and split a large test suite across several runners.
  • Fail fast: run lint and unit tests before slow integration tests.
  • Run only what is needed, for example with path filters so a docs change does not trigger a full build.
  • Use smaller base images and avoid downloading large files on every run.
  • Move slow end-to-end or nightly checks to a scheduled pipeline.
Q72How would you design a CI/CD pipeline for a machine learning API service?
  1. On a pull request: lint, type check, run unit tests, and run a small test that loads the model and checks the API response format. Scan dependencies and check for committed secrets. Branch protection requires all of these to pass.
  2. On merge to main: build the Docker image, tag it with the commit hash, scan the image and push it to the registry.
  3. Deploy to staging by pulling that exact image, then run smoke tests and a quick check of model quality on a fixed test set.
  4. Deploy to production after approval, using a canary or rolling release, with health checks that trigger automatic rollback if they fail.
  5. After release: monitor latency, errors and prediction drift, and keep a scheduled retraining pipeline that promotes a new model only if it passes the evaluation gate.

Secrets live in the CI secret store, the model file comes from a model registry or storage and is not committed to Git, and every step is defined as code in the repository.
