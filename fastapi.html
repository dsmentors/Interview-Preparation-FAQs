FastAPI fundamentals

Q1What is FastAPI, and why is it popular?

FastAPI is a modern Python web framework for building APIs. It is built on Starlette (the web and async parts) and Pydantic (data validation), and it uses standard Python type hints to define what each endpoint accepts and returns.

Why developers like it:

  • Fast to write: type hints give you validation, serialization and editor autocompletion with little code.
  • Automatic interactive documentation (Swagger UI and ReDoc).
  • Async support and very good performance for a Python framework.
  • Dependency injection built in.
  • Standards-based: it generates OpenAPI and JSON Schema.

Q3What are Starlette, Pydantic, Uvicorn and ASGI?
  • Starlette: a lightweight ASGI toolkit that FastAPI builds on for routing, requests, responses, middleware and WebSockets.
  • Pydantic: the library that validates and parses data using Python type hints.
  • ASGI (Asynchronous Server Gateway Interface): the async successor to WSGI. It supports async code, WebSockets and long-lived connections.
  • Uvicorn: an ASGI server that actually runs your FastAPI app and handles the network connections.
Q4How do you create and run a simple FastAPI app?
# main.py
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def read_root():
    return {"message": "Hello, World"}

Run it with Uvicorn (with auto-reload for development):

uvicorn main:app --reload

Here main is the file name and app is the FastAPI object. Newer versions also provide a CLI: fastapi dev main.py.

Q5How does FastAPI generate API documentation automatically?

FastAPI reads your route definitions, type hints and Pydantic models and builds an OpenAPI schema, available at /openapi.json. From it, two interactive documentation pages are served automatically:

  • Swagger UI at /docs, where you can try requests directly in the browser.
  • ReDoc at /redoc, a clean read-only reference.

You can improve the docs with summary, description, tags and examples on your endpoints and models.

Q6What is OpenAPI?

OpenAPI is a standard, language-independent format (JSON or YAML) for describing REST APIs: their paths, parameters, request and response schemas and authentication. Because the description is machine-readable, tools can generate documentation, client libraries and tests from it.

Requests and responses

Q7What are path parameters and query parameters?
  • Path parameters are part of the URL path and identify a resource, for example /items/42.
  • Query parameters come after ? and are usually optional filters or options, for example /items?skip=0&limit=10.
@app.get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None):
    return {"item_id": item_id, "q": q}

item_id is a path parameter (converted and validated as an int), and q is an optional query parameter.

Q8How do you add validation to query and path parameters?

Use Query, Path and Annotated to add constraints:

from typing import Annotated
from fastapi import FastAPI, Query, Path

app = FastAPI()

@app.get("/search/{category_id}")
def search(
    category_id: Annotated[int, Path(ge=1)],
    q: Annotated[str, Query(min_length=3, max_length=50)],
    limit: Annotated[int, Query(ge=1, le=100)] = 10,
):
    return {"category": category_id, "q": q, "limit": limit}

A parameter without a default value is required. Invalid values return a 422 error with a description of what is wrong.

Q9How do you receive a JSON request body?

Declare a parameter whose type is a Pydantic model. FastAPI reads the JSON body, validates it against the model and gives you a Python object.

from pydantic import BaseModel

class Item(BaseModel):
    name: str
    price: float
    in_stock: bool = True

@app.post("/items")
def create_item(item: Item):
    return item
Q10Can you show a simple CRUD API with FastAPI?
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    name: str
    price: float

items: dict[int, Item] = {}          # in-memory store, for demonstration only

@app.post("/items/{item_id}", status_code=201)
def create_item(item_id: int, item: Item):
    if item_id in items:
        raise HTTPException(status_code=409, detail="Item already exists")
    items[item_id] = item
    return item

@app.get("/items/{item_id}", response_model=Item)
def read_item(item_id: int):
    if item_id not in items:
        raise HTTPException(status_code=404, detail="Item not found")
    return items[item_id]

@app.put("/items/{item_id}", response_model=Item)
def update_item(item_id: int, item: Item):
    if item_id not in items:
        raise HTTPException(status_code=404, detail="Item not found")
    items[item_id] = item
    return item

@app.delete("/items/{item_id}", status_code=204)
def delete_item(item_id: int):
    items.pop(item_id, None)
Q11What is response_model, and why use it?

response_model tells FastAPI the shape of the response. FastAPI then validates, filters and documents the output. Its most important use is to keep private fields out of responses, for example never returning a password:

class UserCreate(BaseModel):
    email: str
    password: str

class UserOut(BaseModel):
    id: int
    email: str

@app.post("/users", response_model=UserOut, status_code=201)
def create_user(user: UserCreate):
    return save_user(user)       # extra fields such as the password are filtered out
Q12How do you set HTTP status codes and handle errors?

Set the success code in the decorator (status_code=201) and raise HTTPException for errors:

from fastapi import HTTPException

raise HTTPException(status_code=404, detail="Item not found")

For custom error handling across the whole app, register an exception handler with @app.exception_handler(MyError) and return a JSONResponse.

Q13Why does FastAPI return a 422 error?

422 Unprocessable Content (previously “Unprocessable Entity”) is returned when the request is well-formed HTTP but fails validation: a missing required field, a wrong type, or a value that breaks a constraint. The response body lists each error with its location (loc), message (msg) and type, so the client can see exactly what to fix.

Q14How do you handle form data and file uploads?

Install python-multipart, then use Form, File and UploadFile:

from fastapi import FastAPI, File, Form, UploadFile

app = FastAPI()

@app.post("/upload")
async def upload(title: str = Form(), file: UploadFile = File()):
    content = await file.read()
    return {"title": title, "filename": file.filename, "size": len(content)}

UploadFile streams large files to a temporary file on disk instead of loading everything into memory.

Pydantic and data models

Q15What is Pydantic, and how does FastAPI use it?

Pydantic validates and converts data according to type hints. FastAPI uses Pydantic models to parse request bodies, validate input, serialize responses and generate the JSON Schema used in the docs. If the data does not match the model, a clear validation error is returned automatically.

Q16How do you add custom validation to a Pydantic model?
from pydantic import BaseModel, Field, field_validator

class User(BaseModel):
    name: str = Field(min_length=2)
    age: int

    @field_validator("age")
    @classmethod
    def age_must_be_positive(cls, v):
        if v <= 0:
            raise ValueError("age must be positive")
        return v

Field adds simple constraints, and a field_validator handles custom rules.

Q17What is the difference between Pydantic v1 and v2?

Pydantic v2 was rewritten with a core in Rust, so it is much faster, and it renamed several methods:

Pydantic v1 Pydantic v2
.dict() .model_dump()
.parse_obj() .model_validate()
@validator @field_validator
class Config: model_config = ConfigDict(...)

Current FastAPI versions work with Pydantic v2.

Q18Why should request and response models be separate?

The data a client sends is not the same as the data you return or store. For example, a create model has a password, while the output model has an id and no password, and an update model makes every field optional. Separate models keep secrets out of responses, make each endpoint’s contract clear and prevent clients from setting fields they should not control (such as id or is_admin).

Dependency injection and app structure

Q19What is dependency injection in FastAPI, and how does Depends work?

A dependency is a function that FastAPI runs before your endpoint and whose result it passes in as an argument. You declare it with Depends. It is used for database sessions, authentication, pagination parameters, settings and any shared logic.

from fastapi import Depends

def pagination(skip: int = 0, limit: int = 10):
    return {"skip": skip, "limit": limit}

@app.get("/items")
def list_items(page: dict = Depends(pagination)):
    return page

Dependencies can depend on other dependencies, are cached per request, and make endpoints easy to test because you can replace them with app.dependency_overrides.

Q20How do you manage a database session with dependencies?

Use a dependency with yield, so the session is created for each request and always closed afterwards:

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@app.get("/users/{user_id}")
def get_user(user_id: int, db: Session = Depends(get_db)):
    return db.get(User, user_id)
Q21How do you organize a larger FastAPI project?

Split the app into modules with APIRouter, and include them in the main app:

# routers/users.py
from fastapi import APIRouter

router = APIRouter(prefix="/users", tags=["users"])

@router.get("/")
def list_users():
    return []

# main.py
from fastapi import FastAPI
from routers import users

app = FastAPI()
app.include_router(users.router)

A common layout separates routers/, schemas/ (Pydantic models), models/ (database models), services/ (business logic), dependencies/ and core/ (settings).

Q22How do you manage configuration and secrets?

Keep configuration in environment variables and read it with pydantic-settings, which validates the values and gives you a typed settings object:

from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str
    secret_key: str

settings = Settings()          # reads environment variables (and a .env file if configured)

Never commit secrets to the repository.

Q23What are lifespan events, and what are they used for?

A lifespan function runs code once when the app starts and once when it shuts down. It is used to open database connection pools, load a machine learning model, or create shared HTTP clients, and then close them cleanly.

from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.db_pool = await create_pool()      # startup
    yield
    await app.state.db_pool.close()              # shutdown

app = FastAPI(lifespan=lifespan)

Lifespan replaces the older @app.on_event("startup") and @app.on_event("shutdown") handlers.

Q24What is middleware in FastAPI?

Middleware is code that runs for every request before it reaches your endpoint, and for every response before it is sent. Typical uses are logging, timing, adding headers, compression and CORS. You can add built-in middleware with app.add_middleware(...) or write your own with @app.middleware("http").

Async, performance and background work

Q25What is the difference between def and async def endpoints?
  • async def endpoints run directly on the event loop. Use them when you await async libraries (an async database driver, httpx.AsyncClient).
  • def endpoints are run by FastAPI in a separate thread pool, so a blocking call does not freeze the server.

If you are not sure, a normal def is safe. The mistake to avoid is using blocking code, such as time.sleep(), the requests library or heavy CPU work, inside an async def endpoint, because it blocks the whole event loop and every other request waits.

Q26How does FastAPI achieve high performance?

It runs on an ASGI server (Uvicorn), uses Starlette for the web layer, and uses Pydantic’s fast validation (Rust-based in v2). Async endpoints allow one process to handle many concurrent I/O-bound requests (database or API calls) without waiting for each to finish. In practice, your database and external calls usually matter more than the framework itself, and CPU-heavy work needs separate processes or workers.

Q27What are BackgroundTasks, and when would you use Celery instead?

BackgroundTasks runs a small function after the response has been sent, for example sending an email or writing a log:

from fastapi import BackgroundTasks

def write_log(message: str):
    with open("log.txt", "a") as f:
        f.write(message + "\n")

@app.post("/send")
def send(background_tasks: BackgroundTasks):
    background_tasks.add_task(write_log, "email sent")
    return {"status": "queued"}

It runs inside the same process, so use a task queue such as Celery (or RQ, Arq) with a message broker for heavy, long-running or critical jobs that need retries, scheduling and to survive a restart.

Q28How do you enable CORS?

CORS controls which browser origins may call your API. Add the built-in middleware and list the allowed origins:

from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://example.com"],
    allow_methods=["*"],
    allow_headers=["*"],
)

Avoid allow_origins=["*"] in production, especially when you allow credentials.

Q29Does FastAPI support WebSockets and streaming?

Yes.

  • WebSockets: use @app.websocket("/ws") for two-way, real-time communication such as chat or live updates.
  • Streaming responses: return a StreamingResponse to send data in chunks. This is commonly used to stream text from an LLM token by token (often with Server-Sent Events) or to send large files.

Security, database, testing and deployment

Q30How do you implement authentication in FastAPI?

FastAPI includes security helpers. A common approach is OAuth2 with a bearer token (JWT): the client logs in, receives a token, and sends it in the Authorization: Bearer ... header. A dependency verifies the token and returns the current user.

from typing import Annotated
from fastapi import Depends
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]):
    payload = decode_jwt(token)          # verify the signature and expiry, raise 401 if invalid
    return get_user(payload["sub"])

@app.get("/me")
def read_me(user: Annotated[User, Depends(get_current_user)]):
    return user

Here decode_jwt and get_user are your own functions. Other options are API keys in headers and external identity providers.

Q31How should you store passwords?

Never store plain text passwords. Store a salted hash created with a slow, purpose-built algorithm such as Argon2 or bcrypt, and verify logins by hashing the submitted password and comparing it with the stored hash.

Q32How do you connect FastAPI to a database?

Common choices are SQLAlchemy (sync or async) or SQLModel (which combines SQLAlchemy and Pydantic). The pattern is:

  1. Create the engine and a session factory.
  2. Provide a session through a dependency with yield (one session per request).
  3. Use separate Pydantic schemas for the API and ORM models for the tables.
  4. Use a migration tool such as Alembic to change the schema safely.

For high-concurrency apps, use an async driver (for example asyncpg) with SQLAlchemy’s async engine, and use async def endpoints.

Q33How do you test a FastAPI application?

Use TestClient with pytest. It calls your app directly without starting a server.

from fastapi.testclient import TestClient
from main import app

client = TestClient(app)

def test_read_item_not_found():
    response = client.get("/items/999")
    assert response.status_code == 404
    assert response.json()["detail"] == "Item not found"

Use app.dependency_overrides to replace the real database or authentication with test versions.

Q34How do you deploy a FastAPI app?
  • Run it with an ASGI server: uvicorn main:app --host 0.0.0.0 --port 8000.
  • For several processes, use multiple Uvicorn workers (--workers 4) or run it under Gunicorn with Uvicorn workers.
  • Package it in a Docker image and run it on a platform of your choice (a VM, Kubernetes or a managed service).
  • Put it behind a reverse proxy such as Nginx or a cloud load balancer that handles HTTPS.
  • Configure it with environment variables, and add health checks, logging and monitoring.
Q35How would you serve a machine learning model with FastAPI?

Load the model once at startup (not on every request), define the input with a Pydantic model, and expose a prediction endpoint.

from contextlib import asynccontextmanager
from fastapi import FastAPI
from pydantic import BaseModel
import joblib

models = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    models["clf"] = joblib.load("model.joblib")     # load once at startup
    yield
    models.clear()

app = FastAPI(lifespan=lifespan)

class Features(BaseModel):
    age: float
    income: float

@app.post("/predict")
def predict(features: Features):
    prediction = models["clf"].predict([[features.age, features.income]])[0]
    return {"prediction": int(prediction)}

For production, also add input validation limits, logging, a health endpoint, model versioning and, for heavy models, batching or a separate inference service.

Q36How do you version an API and add rate limiting?
  • Versioning: put the version in the path (/api/v1/...) and use a separate APIRouter for each version, so old clients keep working.
  • Rate limiting: FastAPI has no built-in rate limiter. Use a library such as slowapi, or do it at the API gateway or reverse proxy, often backed by Redis.
Q37What are some best practices for building FastAPI applications?
  • Use type hints and Pydantic models everywhere, with separate request and response schemas.
  • Keep endpoints thin and put business logic in a service layer.
  • Use dependency injection for database sessions, settings and authentication.
  • Never block the event loop in async def endpoints.
  • Handle errors consistently with clear messages and the right status codes.
  • Keep secrets in environment variables and use HTTPS.
  • Write tests, and add logging and monitoring.
