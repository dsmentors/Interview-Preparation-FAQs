Approach and fundamentals

Q1How do you approach a system design interview?

Use a clear, repeatable structure and talk through it:

  1. Clarify requirements: functional (what the system does) and non-functional (scale, latency, availability, consistency). Agree on the scope.
  2. Estimate the scale: users, requests per second, data size, bandwidth.
  3. Define the API and the main data model.
  4. Draw the high-level design: clients, load balancer, services, databases, caches, queues.
  5. Deep dive into the one or two hardest parts (data storage, scaling, the core algorithm).
  6. Find bottlenecks and failure points, and discuss trade-offs and improvements.
  7. Summarize the design and what you would do next.

State your assumptions out loud, and drive the conversation instead of waiting for questions.

Q2What are functional and non-functional requirements?
  • Functional: what the system must do (“users can post photos, follow others and see a feed”).
  • Non-functional: the qualities it must have: scalability, availability, latency, throughput, consistency, durability, security, cost, maintainability.

Non-functional requirements usually drive the architecture. For example, “99.99% availability and 100 ms response” leads to very different designs from a nightly batch report.

Q3How do you do back-of-the-envelope estimation? (worked example)

Round numbers and write down assumptions. Useful facts: a day has about 86,400 seconds (~10⁵), so 1 million requests per day is about 12 requests per second.

Example: a URL shortener

  • 100 million new URLs per month ⇒ about 40 writes per second.
  • Reads are 100 times more frequent ⇒ about 4,000 reads per second (peak maybe 2 to 3 times higher).
  • Storage for 5 years: 100M × 12 × 5 = 6 billion URLs, at about 500 bytes each ⇒ about 3 TB.
  • A 7-character code from 62 characters gives 62⁷ ≈ 3.5 trillion combinations, which is more than enough.

Estimates show whether you need one database or sharding, and whether caching is essential.

Q4What are some latency numbers every engineer should know?

Approximate orders of magnitude:

Operation Time
Read from main memory (RAM) ~100 nanoseconds
Read from an SSD (random) ~100 microseconds
Round trip within the same data center ~0.5 milliseconds
Read 1 MB sequentially from SSD ~1 millisecond
Disk (HDD) seek ~10 milliseconds
Round trip across continents ~100 to 150 milliseconds

The lesson: memory is much faster than disk, and disk is much faster than the network across regions. That is why caching and data locality matter.

Q5What is the difference between vertical and horizontal scaling?
Vertical scaling (scale up) Horizontal scaling (scale out)
How Bigger machine (more CPU, RAM) More machines behind a load balancer
Complexity Simple Needs distributed design (state, data, coordination)
Limit Hardware ceiling, and a single point of failure Practically very large
Cost Gets expensive at the top end Commodity hardware

Large systems scale horizontally, which works best with stateless services, because any server can handle any request.

Q6What is the difference between latency, throughput and bandwidth?
  • Latency: how long one request takes (milliseconds). Look at percentiles (p50, p95, p99), not only the average.
  • Throughput: how many requests or operations are completed per unit of time (requests per second).
  • Bandwidth: the maximum amount of data that can be transferred per second over a link.

Improving one can hurt another, for example batching increases throughput but also increases latency.

Q7What are availability, reliability, SLA, SLO and SLI?
  • Availability: the fraction of time the system is working. “Three nines” (99.9%) allows about 8.8 hours of downtime per year, and “four nines” (99.99%) about 53 minutes.
  • Reliability: the system keeps working correctly, even when failures happen.
  • SLI (indicator): a measured metric (for example the share of successful requests).
  • SLO (objective): the target for that metric (99.9% success over 30 days).
  • SLA (agreement): a contract with customers, usually with penalties if it is not met.
Q8What is the CAP theorem?

In a distributed data store, when a network partition (P) happens, you can guarantee only one of:

  • Consistency (C): every read sees the latest write.
  • Availability (A): every request gets a response (even if it may be stale).

Partitions cannot be avoided in real networks, so the real choice is CP or AP during a partition. A CP system (for example a strongly consistent store) may reject requests, while an AP system (for example Dynamo-style stores) stays available but may return stale data. When there is no partition, the trade-off is between latency and consistency (the PACELC extension).

Core building blocks

Q9What does a load balancer do, and what algorithms does it use?

A load balancer distributes incoming requests across several servers, removes unhealthy servers (health checks) and avoids a single point of failure.

Algorithm How it works
Round robin Each server in turn
Weighted round robin More requests to stronger servers
Least connections The server with the fewest active connections
IP hash The same client goes to the same server
Consistent hashing Keeps related keys on the same server, with little reshuffling when servers change

Layer 4 balancers work on IP and port (fast, simple), and Layer 7 balancers understand HTTP (route by URL, headers or cookies, and can terminate TLS). Load balancers themselves should be redundant.

Q10What are a reverse proxy and an API gateway?
  • A reverse proxy (for example Nginx) sits in front of servers and forwards client requests: it can do load balancing, caching, compression and TLS termination.
  • An API gateway is a reverse proxy specialized for APIs. It is the single entry point that handles authentication, rate limiting, routing to the right microservice, request transformation and monitoring.
Q11What are the main caching strategies?
Strategy How it works Trade-off
Cache-aside (lazy loading) App checks the cache, on a miss reads the DB and fills the cache Simple, but the first request is slow and data can become stale
Read-through The cache itself loads data from the DB on a miss Cleaner code, depends on the cache provider
Write-through Writes go to the cache and the DB together Consistent, but slower writes
Write-back (write-behind) Writes go to the cache, and are saved to the DB later Fast writes, but data can be lost if the cache fails
Write-around Writes go straight to the DB, skipping the cache Avoids filling the cache with rarely read data

Common eviction policies: LRU (least recently used), LFU (least frequently used) and TTL (time to live).

Q12What is cache invalidation, and what is a cache stampede?

Cache invalidation is keeping cached data consistent with the source: use a TTL, delete or update the key on writes, or use events. It is famously hard to get right.

A cache stampede (thundering herd) happens when a popular key expires and many requests hit the database at once. Solutions: locking or request coalescing (only one request rebuilds the value), jittered TTLs (so keys do not expire together), refreshing the value before it expires, and serving slightly stale data while refreshing.

Q13What is a CDN, and when do you use it?

A Content Delivery Network is a set of servers spread around the world that cache content close to users, mostly static files (images, video, scripts, CSS) and sometimes API responses. It reduces latency, bandwidth and load on your origin servers, and helps absorb traffic spikes.

  • Pull CDN: the edge fetches content from the origin on the first request.
  • Push CDN: you upload content to the CDN in advance.

Control freshness with cache headers and versioned file names.

Q14SQL vs NoSQL: how do you choose?
SQL (relational) NoSQL
Data model Tables, fixed schema Key-value, document, wide-column, graph
Consistency Strong, ACID transactions Often eventual (configurable)
Queries Powerful joins and SQL Simple access patterns, joins are limited
Scaling Vertical first, sharding is harder Designed to scale out horizontally
Examples PostgreSQL, MySQL Redis, DynamoDB, MongoDB, Cassandra, Neo4j

Choose SQL when data is relational and you need transactions and flexible queries. Choose NoSQL for massive scale, flexible schemas or a specific access pattern (for example key lookups or time-series). Many systems use both.

Q15What are database indexes, and what is their cost?

An index is a data structure (usually a B-tree) that lets the database find rows without scanning the whole table, turning an O(n) scan into roughly O(log n). The cost: extra storage and slower writes, because every insert and update must also update the indexes. Index the columns used in filters, joins and sorting, and avoid indexing everything. LSM-tree based stores (Cassandra, RocksDB) optimize for fast writes instead.

Q16What are database replication strategies?
  • Leader-follower (primary-replica): writes go to the leader, which copies changes to followers. Followers serve reads and take over if the leader fails. Replication can be synchronous (safer, slower) or asynchronous (faster, but followers can lag and data may be lost on failover).
  • Multi-leader: several nodes accept writes (useful across regions), but you must resolve write conflicts.
  • Leaderless (Dynamo-style): any node accepts reads and writes, and quorums decide success: with N replicas, W write acknowledgments and R read acknowledgments, choose R + W > N for strong consistency.
Q17What is sharding (partitioning), and what are its challenges?

Sharding splits data across several databases or nodes, so no single machine holds everything.

Strategy How Issue
Range-based By ranges of the key (A–F, G–M...) Hot spots if data is uneven
Hash-based hash(key) % number_of_shards Even spread, but resharding moves a lot of data (use consistent hashing)
Directory-based A lookup table maps keys to shards Flexible, but the directory is a dependency

Challenges: hot partitions (for example a celebrity user), cross-shard joins and transactions, rebalancing, and choosing a good shard key.

Q18What are message queues and streaming platforms (Kafka, RabbitMQ), and why use them?

A message queue lets services communicate asynchronously: producers put messages on a queue, and consumers process them later. It decouples services, absorbs traffic spikes (buffering), allows retries and makes it easy to scale consumers.

  • Kafka is a distributed, durable log: messages are written to topics split into partitions, kept for a retention period, and read by consumer groups with offsets. Ordering is guaranteed within a partition.
  • RabbitMQ / SQS are traditional queues where messages are removed after being consumed.

Delivery guarantees: at-most-once, at-least-once (the common default, so consumers must be idempotent) and exactly-once (achieved with idempotence or transactions).

Distributed systems concepts

Q19What is consistent hashing, and why is it used?

With simple hash(key) % N, changing the number of servers N remaps almost every key, which empties caches and moves data. Consistent hashing places servers and keys on a ring, and each key belongs to the next server clockwise. Adding or removing a server moves only about 1/N of the keys. Virtual nodes (each server appears many times on the ring) balance the load.

import bisect
import hashlib

class ConsistentHash:
    def __init__(self, nodes, replicas=100):
        self.ring = []                                   # sorted list of (hash, node)
        for node in nodes:
            for i in range(replicas):
                self.ring.append((self._hash(f"{node}#{i}"), node))
        self.ring.sort()
        self.keys = [h for h, _ in self.ring]

    @staticmethod
    def _hash(value):
        return int(hashlib.md5(value.encode()).hexdigest(), 16)

    def get_node(self, key):
        idx = bisect.bisect(self.keys, self._hash(key)) % len(self.keys)
        return self.ring[idx][1]

ring = ConsistentHash(["server-1", "server-2", "server-3"])
print(ring.get_node("user:42"))
Q20What is the difference between ACID and BASE?
  • ACID (relational databases): Atomicity, Consistency, Isolation, Durability. Strong guarantees for transactions.
  • BASE (many NoSQL systems): Basically Available, Soft state, Eventually consistent. Favors availability and scale over immediate consistency.
Q21What consistency models should you know?
  • Strong consistency: after a write, every read sees it. Simplest to reason about, slower and less available.
  • Eventual consistency: replicas converge over time, and reads may be stale for a while.
  • Read-your-writes: a user always sees their own updates.
  • Causal consistency: related events are seen in the same order by everyone.

Choose the weakest model that is acceptable for the feature: a bank balance needs strong consistency, a like counter does not.

Q22How do distributed transactions work? (2PC vs Saga)
  • Two-Phase Commit (2PC): a coordinator asks all participants to prepare, then tells them all to commit (or abort). It gives atomicity, but it is blocking and the coordinator is a point of failure, so it is rarely used across microservices.
  • Saga: a sequence of local transactions, each with a compensating action that undoes it if a later step fails (for example “refund payment” if “reserve stock” fails). It gives eventual consistency without locking across services, and can be orchestrated (a central coordinator) or choreographed (services react to events).
Q23What is idempotency, and why is it important in distributed systems?

An operation is idempotent if repeating it has the same effect as doing it once. Because networks fail and clients retry, requests and messages can be delivered more than once, so a payment must not be charged twice.

Techniques: an idempotency key sent by the client and stored by the server (return the saved result for a repeated key), unique constraints in the database, and upserts instead of blind inserts.

Q24How do you handle failures: retries, timeouts, backoff and circuit breakers?
  • Timeouts: never wait forever for a dependency.
  • Retries with exponential backoff and jitter: wait longer after each failure, with random variation, to avoid synchronized retry storms. Only retry idempotent operations.
  • Circuit breaker: after repeated failures, stop calling the failing service for a while (open state), then try again carefully (half-open). It prevents cascading failures.
  • Bulkheads: isolate resources so one failing part cannot exhaust everything.
  • Fallbacks and graceful degradation: return cached or simplified data instead of failing completely.
Q25What is consensus, and what are Raft and Paxos?

Consensus is how several nodes agree on a single value (for example who the leader is, or the order of log entries) even if some nodes fail. Paxos and Raft are consensus algorithms. Raft is designed to be easier to understand: nodes elect a leader, the leader appends entries to a replicated log, and an entry is committed once a majority (quorum) has stored it. They are the basis of systems such as etcd and ZooKeeper-like coordination services.

Q26Monolith vs microservices: what are the trade-offs?

Q27REST vs gRPC vs GraphQL, and synchronous vs asynchronous communication?

Synchronous calls (request-response) are simple, but the caller waits and is affected by failures. Asynchronous messaging (queues, events) decouples services and improves resilience, but is harder to follow and debug.

Q29What is observability: logs, metrics and traces?
  • Logs: records of events, for debugging specific cases (structured, with request IDs).
  • Metrics: numeric measurements over time (request rate, error rate, latency percentiles, CPU), for dashboards and alerts.
  • Traces: the path of one request across services (distributed tracing, for example with OpenTelemetry), to find where time is spent.

Together they let you detect, diagnose and fix problems. Alert on user-facing symptoms (error rate, latency), not only on machine metrics.

Classic system design problems

Q30Design a URL shortener (like bit.ly).

Requirements: create a short link for a long URL, redirect quickly, optional expiry and analytics. Read-heavy (about 100:1). Estimates are in the estimation question above (about 40 writes per second, 4,000 reads per second, about 3 TB over 5 years).

API: POST /shorten {url} returns a short code, and GET /{code} returns a redirect (HTTP 301 or 302).

Generating the code: take a unique number (from a counter or a distributed ID generator) and encode it in base62. This avoids collisions. Hashing the URL and truncating needs collision handling.

import string

ALPHABET = string.digits + string.ascii_letters            # 62 characters

def encode_base62(n):
    if n == 0:
        return ALPHABET[0]
    chars = []
    while n:
        n, r = divmod(n, 62)
        chars.append(ALPHABET[r])
    return "".join(reversed(chars))

def decode_base62(s):
    n = 0
    for ch in s:
        n = n * 62 + ALPHABET.index(ch)
    return n

print(encode_base62(125))       # 21

Storage: a key-value or SQL table code → long_url, created_at, expiry (sharded by code when it gets large).

Scaling reads: a cache (for example Redis) for hot links, a CDN or many stateless servers behind a load balancer. 302 redirects allow counting clicks, 301 are cacheable by browsers.

Other points: avoid guessable sequences if privacy matters, rate limit creation, handle expired and deleted links, and push analytics events to a queue.

Q31Design a rate limiter.

Goal: limit how many requests a client can make in a time window (protect against abuse and overload). It sits in the API gateway or as middleware, and is keyed by user, IP or API key.

Algorithm Idea Notes
Fixed window counter Count requests per time window Simple, but allows bursts at window edges
Sliding window log Store request timestamps Accurate, uses more memory
Sliding window counter Weighted mix of the current and previous windows Good balance
Token bucket Tokens refill at a constant rate, each request uses one Allows bursts, very common
Leaky bucket Requests leave the queue at a fixed rate Smooths traffic 
import time

class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate = rate                      # tokens added per second
        self.capacity = capacity              # maximum burst size
        self.tokens = capacity
        self.updated = time.monotonic()

    def allow(self):
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
        self.updated = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

Distributed version: keep the counters in Redis and update them atomically (for example with INCR and EXPIRE, or a Lua script), so all servers share the same limits. Return HTTP 429 with a Retry-After header, and decide whether to fail open or closed if the limiter is unavailable.

Q32Design a news feed (timeline) system.

Core question: when a user opens the app, how do you build the list of posts from the people they follow?

  • Fan-out on write (push): when a user posts, copy the post ID into each follower’s feed (stored in a cache or database). Reads are fast, but writes are expensive for users with millions of followers.
  • Fan-out on read (pull): when a user opens the feed, fetch recent posts of everyone they follow and merge them. Writes are cheap, but reads are slow.
  • Hybrid: push for normal users, pull for celebrities (merge their posts at read time).

Components: a post service, a follow graph, a feed service with a feed cache (Redis lists of post IDs), a ranking service (recency or ML ranking), a media CDN, and queues for fan-out workers. Paginate with cursors, and store posts in a sharded database.

Q33Design a chat or messaging system (like WhatsApp).
  • Connections: clients keep a WebSocket connection to a chat server. A session or presence service knows which server each user is connected to.
  • Sending: the sender’s server stores the message, finds the recipient’s server and forwards it. If the recipient is offline, store it and send a push notification.
  • Storage: messages are write-heavy, so use a store that scales for writes (for example Cassandra or HBase), keyed by chat and message ID.
  • Ordering and IDs: use per-chat, time-ordered unique IDs (Snowflake-style).
  • Group chats: fan out to all members (limit the group size).
  • Delivery receipts: sent, delivered and read status through acknowledgments.
  • Other: media in object storage with a CDN, end-to-end encryption, and message queues between services.
Q34Design a notification system.
  1. Producers (services) send notification requests to an API.
  2. A notification service validates, applies user preferences (opt-outs, quiet hours), de-duplicates and renders templates.
  3. Messages go into queues, one per channel and priority (push, email, SMS), so a spike in one does not block the others.
  4. Workers send them through providers (APNs and FCM for mobile push, an email service, an SMS gateway) with retries and backoff.
  5. Store status and logs (sent, delivered, failed) for tracking.

Points to cover: rate limiting per user, priority (a security alert before marketing), idempotency to avoid duplicates, scalability through partitioned queues, and analytics.

Q35Design a web crawler.

Components:

  • URL frontier: a queue of URLs to crawl, with priority and politeness (a limit per domain, respecting robots.txt and crawl delays).
  • Fetchers: many workers that download pages (with a DNS cache and timeouts).
  • Parser: extracts text and links.
  • Duplicate detection: do not crawl the same URL twice (a Bloom filter or a set of URL hashes) and detect duplicate content (content hashes).
  • Storage: raw pages in object storage, extracted data and an index in a database or search engine.
  • Scheduler for re-crawling frequently changing pages.

Scale by partitioning the URLs by domain across workers, and handle traps (infinite URL spaces) with depth and size limits.

Q36Design a distributed key-value store (like Dynamo).
  • Partitioning: spread keys over nodes with consistent hashing and virtual nodes.
  • Replication: store each key on N nodes (the next nodes on the ring), across racks or zones.
  • Consistency: tunable quorums (R, W, with R + W > N for strong consistency), with eventual consistency available for speed.
  • Conflict handling: vector clocks or last-write-wins, and read repair.
  • Failure handling: gossip protocol to detect failed nodes, hinted handoff (another node holds writes temporarily), and anti-entropy with Merkle trees to repair replicas.
  • Storage engine: a write-optimized LSM tree (a write-ahead log, an in-memory table and sorted files on disk).
Q37Design a file storage and sync service (like Dropbox).
  • Split files into chunks (for example 4 MB), and store them in object storage, keyed by their content hash. Identical chunks are stored once (deduplication), and only changed chunks are uploaded on an edit (delta sync).
  • A metadata service and database stores the file tree, versions, chunk lists and permissions.
  • A sync service and notification channel tells the other devices about changes (long polling or WebSockets), and they download the new chunks.
  • Handle conflicts (two edits at the same time) by creating a conflicted copy, keep versions for restore, and apply access control and encryption.
Q38How do you generate unique IDs in a distributed system?
Approach Pros Cons
Database auto-increment Simple, ordered Single point of failure, hard to scale
UUID (random) No coordination Large (128 bits), not time-ordered, bad for index locality
Snowflake-style ID 64 bits, roughly time-ordered, no central database Needs unique machine IDs and a reasonable clock
Ticket server / range allocation Simple, ordered by range Needs a central service (make it redundant)

A Snowflake ID combines a timestamp, a machine ID and a sequence number, so each machine can generate IDs independently.

Machine learning and AI system design

Q39What is the framework for an ML system design interview?
  1. Clarify the business goal and the success metrics (business metric, and the ML metric that supports it).
  2. Frame it as an ML problem: the task (classification, ranking, regression), the inputs and outputs, and the constraints (latency, scale, cost, privacy).
  3. Data: sources, labels (and how to get them), volume, quality, bias and privacy.
  4. Features: what signals matter, and how they are computed in training and serving (a feature store).
  5. Modeling: start with a simple baseline, then more complex models, with trade-offs.
  6. Training: pipeline, validation, offline metrics, and retraining schedule.
  7. Serving: batch vs online, latency budget, scaling, caching, fallbacks.
  8. Evaluation: offline metrics, then A/B tests for online impact.
  9. Monitoring and iteration: data drift, model quality, feedback loops, and retraining.
Q40Design a recommendation system (for videos, products or posts).

Use a multi-stage funnel, because scoring millions of items with a heavy model is too slow:

  1. Candidate generation (retrieval): quickly narrow millions of items to hundreds or thousands, using a two-tower model (user and item embeddings) with approximate nearest neighbor (ANN) search, plus collaborative filtering, popular items and recent activity.
  2. Ranking: a more powerful model (for example gradient boosting or a deep model) scores each candidate with rich features (user history, item data, context) to predict click, watch time or purchase.
  3. Re-ranking: apply business rules, diversity, freshness, fairness and removal of already-seen items.

Cold start: use content features, popularity, onboarding questions and exploration for new users and items. Metrics: offline (recall@k, NDCG), online (click-through rate, watch time, retention, revenue) through A/B tests. Risks: feedback loops, popularity bias and filter bubbles, so add exploration. Serving: precomputed embeddings, a feature store, caching and a latency budget for each stage.

Q41Design a real-time fraud detection system.
  • Requirements: decide within about 50 to 100 ms whether to approve a transaction, with very imbalanced data and costly mistakes in both directions (missed fraud vs blocking good customers).
  • Data and features: transaction details, user and device history, and velocity features (number of transactions in the last 5 minutes), computed from a streaming pipeline into an online feature store.
  • Models: combine business rules with an ML model (for example gradient boosting), with scores mapped to approve, review or decline using a cost-based threshold.
  • Labels: often delayed (chargebacks arrive weeks later), so use proxy labels and human review, and retrain regularly.
  • Serving: an online scoring service with fallbacks if it fails.
  • Operations: monitor drift and false positive rates, give analysts explanations, and adapt to fraudsters changing their behavior.
Q42How do you design a RAG system at scale?
  • Ingestion pipeline: connectors, layout-aware parsing, chunking with metadata (including access permissions), embeddings, and a vector database plus a keyword index for hybrid search. Update incrementally.
  • Query path: query rewriting → hybrid retrieval → reranking → prompt building with citations → LLM generation (streamed).
  • Latency budget: for example retrieval 100 ms, reranking 100 ms, and the LLM first token under 1 second. Use caching (including a semantic cache for similar questions).
  • Security: enforce per-user permissions at retrieval time and guard against prompt injection from documents.
  • Quality and monitoring: retrieval and faithfulness metrics, user feedback, logging of retrieved chunks, and cost tracking per request.
  • Scaling: shard and replicate the index, batch embedding jobs, and route simple questions to cheaper models.
Q43Design a system to serve a large language model (LLM inference).

LLM serving is limited by GPU memory and compute, and key techniques are:

  • KV cache: store the attention keys and values of earlier tokens, so each new token does not recompute the whole prompt.
  • Continuous batching: add new requests into the running batch at every generation step, which keeps GPUs busy and raises throughput.
  • Efficient memory management (for example paged attention in vLLM) to fit more concurrent requests.
  • Quantization (8-bit or 4-bit weights) to cut memory and cost, at a small quality loss.
  • Model parallelism (tensor or pipeline) to split a large model across GPUs.
  • Streaming responses (SSE or WebSockets) so users see tokens immediately.
  • Speculative decoding and prefix caching (reuse the computed prompt prefix) to cut latency.

Track time to first token (TTFT), tokens per second, queue time and cost per request. Add autoscaling, request routing and rate limits, plus fallbacks and a model router that sends easy requests to smaller models.

Q44How do you handle online vs batch inference in system design?
Batch inference Online (real-time) inference
When Scheduled (hourly, nightly) On each request
Latency Not critical Milliseconds
Cost Efficient, uses the hardware fully Needs always-on, scalable serving
Freshness Predictions can be stale Uses the latest data
Example Daily churn scores, email recommendations Fraud checks, search ranking

A common hybrid is precompute what you can in batch (embeddings, candidate lists) and compute the final, context-dependent step online.

Q45What is a feature store, and where does it fit in an ML system design?

A feature store provides one consistent definition of features for both training (an offline store with history, point-in-time correct) and serving (an online store with low-latency lookups). It prevents training-serving skew, avoids duplicated work and enables feature reuse. In a design, it sits between the data pipelines (batch and streaming) and both the training pipeline and the online prediction service.

Q46How do you evaluate an ML system: offline vs online metrics?
  • Offline metrics (precision, recall, AUC, NDCG, RMSE) are computed on historical data. They are fast and cheap, and used to select candidate models.
  • Online metrics (click-through rate, conversion, retention, revenue, latency) measure the real business impact in production, and are validated with an A/B test.

Offline gains do not always translate to online gains (for example because of feedback loops and changing behavior), so the final decision should rely on online experiments, with guardrail metrics for safety.

Q47How do you monitor an ML system after launch and close the feedback loop?

Monitor system health (latency, errors, throughput, cost), data quality and drift in inputs, prediction distributions, and model quality (when labels arrive, or with proxy metrics). Log inputs, features, predictions and the model version. Collect feedback (clicks, corrections, labels from reviewers) into a dataset for retraining, and set up alerts, a rollback path and a regular retraining schedule. Watch for feedback loops where the model influences its own training data.

Reliability, security and interview strategy

Q48How do you design for high availability and disaster recovery?
  • Remove single points of failure: redundant servers, load balancers and databases (replicas with automatic failover).
  • Spread across availability zones, and across regions for the highest requirements.
  • Health checks, autoscaling and self-healing (replacing failed instances).
  • Backups and tested restores.
  • Define RTO (Recovery Time Objective), how fast you must recover, and RPO (Recovery Point Objective), how much data loss is acceptable. They decide between a cheap cold standby and an expensive active-active setup.
  • Use graceful degradation and chaos testing to prove it works.
Q49How do you handle a hot key or hot partition?

A hot key is a key (a celebrity, a viral item) that gets a disproportionate amount of traffic, overloading one node. Solutions: cache it aggressively (including in a local in-memory cache), replicate the hot data on several nodes, split the key into several sub-keys (for example key#1 to key#10) and combine on read, add a CDN, and use rate limiting or request coalescing.

Q50What security topics should be covered in a system design?
  • Authentication (who you are) and authorization (what you may do): OAuth 2.0, JWT, role-based access control.
  • Encryption in transit (TLS) and at rest.
  • Rate limiting and protection against abuse (DDoS, bots).
  • Input validation and protection against injection attacks.
  • Secrets management and least privilege between services.
  • Audit logs, privacy and compliance (for example data retention and deletion).
Q51How do you control cost in a system design?

Right-size resources and autoscale, use caching and CDNs to cut compute and bandwidth, move cold data to cheaper storage tiers, use reserved or spot instances where possible, avoid over-engineering for a scale you do not have, and measure cost per request or per user. For ML systems, use smaller models, batching, quantization and caching to reduce GPU spend.

Q52What are the common mistakes in system design interviews?
  • Jumping into the solution without clarifying requirements and scale.
  • Skipping estimation or using unrealistic numbers.
  • Drawing a generic diagram with no justification for the choices.
  • Over-engineering (microservices and sharding for a small problem), or ignoring failures and bottlenecks.
  • Not discussing trade-offs (consistency vs availability, cost vs latency).
  • Poor communication: long silences, ignoring the interviewer’s hints.
  • Not covering monitoring, security and data aspects.
Q53How should you prepare for system design interviews?
  • Learn the building blocks (load balancers, caches, queues, databases, sharding, replication) and the trade-offs between them.
  • Practice classic designs (URL shortener, news feed, chat, rate limiter) with a timer, and explain them out loud.
  • Learn the estimation numbers and practice quick calculations.
  • Read engineering blogs and papers (for example about Dynamo, Kafka, Bigtable) and real architectures.
  • For AI roles, also practice ML system design (recommendation, search, fraud, LLM and RAG serving).
  • Ask a friend to do mock interviews and give feedback.
